### 2.9j Cloud connection (`src/lib/cloud-connection/`) — **IMPLEMENTED**, все 3 среза, в `dev`

- **Статус:** срез 1 из 3 (`docs/decisions/0008-cloud-connection.md`, owner instruction, 2026-09-22, Telegram: «Продолжаем тут же. Это нужно для работы полноценного счетчика»). Устанавливает единственный device-persistent Google Cloud OAuth grant, полностью независимый от per-channel YouTube логина (`users`) — цель: реальные числа по лимитам/использованию Google Cloud Quotas/Monitoring API поверх уже существующих счётчиков трафика шлюзов (§2.9k ниже). Этот модуль сам по себе (подключение/статус) не вызывает Cloud Quotas/Monitoring API — реальные вызовы делает §2.9l (срез 3, та же ветка, тоже уже смёржена). Все 3 среза смёржены в `dev` в `4be1f29` (см. `docs/ROADMAP_STATUS.md` BL-061/062/063).
- **Файлы:** `src/lib/cloud-connection/{contracts,schemas,crypto,services,redirect-uri,index}.ts`, `adapters/store.ts`; таблица `cloud_connection` в `src/lib/db.ts` (SCHEMA_MIGRATIONS версия 11, singleton-строка, `getStoredCloudConnection`/`upsertStoredCloudConnection`/`clearStoredCloudConnection`); API-роуты `GET /api/cloud-connection/{start,callback,status}`, `POST /api/cloud-connection/disconnect`; UI `src/components/cloud-connection-settings.tsx` (Settings tab, рядом с `ReadGatewaySettings`).
- **Скоуп:** `https://www.googleapis.com/auth/monitoring.read` **плюс `openid`/`email`** — нужны, чтобы `fetchGoogleIdentity` мог определить email подключённого аккаунта. Найдено живой проверкой: первая реальная попытка подключения падала с "Unable to fetch user identity from Google" до добавления этих двух скоупов, а callback-роут ошибочно пробрасывал такие ошибки дальше (голая страница 500) вместо аккуратного редиректа — исправлено вместе. **Скоуп сужен 2026-09-22** (владелец: «Если он нам действительно не нужен, то зачем нам его оставлять?») с изначального широкого `cloud-platform` (был нужен только для `quotaInfos.list`) до `monitoring.read`, когда §2.9l показал, что Cloud Quotas API вообще не требуется. Сужение уже выданного разрешения требует переподключения аккаунта — Google не понижает scope автоматически.
- **Шифрование:** access/refresh токен хранятся одним AES-256-GCM blob'ом (`ciphertext`/`iv`/`authTag`), ключ — `CLOUD_CONNECTION_ENCRYPTION_KEY`, **намеренно отдельный** от `AI_CONNECTIONS_ENCRYPTION_KEY` (`AGENTS.md` §M — независимость фичевых модулей). В отличие от `users` (RISK-07, plaintext), здесь plaintext сочтён неприемлемым из-за широты запрошенного скоупа — см. RISK-48.
- **Сознательно НЕ добавлена в `SNAPSHOT_TRANSFERRED_TABLES`** — device-local, та же логика, что и `users`/`ai_connection_credentials`: переустанавливается на каждом устройстве через собственный Connect-флоу, никогда не переезжает со snapshot/handoff.
- **Независимость от канала:** подключение/отключение здесь никогда не влияет на активный YouTube-канал, и наоборот — смена канала никогда не отзывает этот grant (собственно требование владельца).
- **Чего явно нет в этом срезе:** ротации/бэкапа ключа шифрования (RISK-48, тот же паттерн, что RISK-15). Реальные числа лимитов/использования — см. §2.9l ниже (срез 3, тоже уже реализован на этой ветке).

### 2.9l Cloud Quotas — реальные числа лимита/использования (`src/lib/cloud-quotas/`) — **IMPLEMENTED**, в `dev`

- **Статус:** срез 3 из 3 плана §2.9j (owner instruction, 2026-09-22, Telegram: «сколько максимальная квота... сколько из неё уже использовано»). Зависит от §2.9j (Cloud connection) для credentials — `resolveCloudCredentials()`.
- **Ключевое открытие живой разведкой (2026-09-22):** Cloud Quotas API (`quotaInfos.list`) оказался НЕ НУЖЕН вообще (в проекте он выключен, 403 SERVICE_DISABLED) — уже работающий Cloud Monitoring API сам по себе отдаёт и лимит (`serviceruntime.googleapis.com/quota/limit`, `limit_name="defaultPerDayPerProject"`, GAUGE), и использование (`serviceruntime.googleapis.com/quota/rate/net_usage`, DELTA, суммируется за 24ч). Реальные подтверждённые цифры на момент разведки: Data API v3 (youtube.googleapis.com) — лимит 10 000/сутки; YouTube Analytics API (youtubeanalytics.googleapis.com) — лимит 100 000/сутки, отдельный пул (те же выводы, что в §2.9k про разделение шлюзов).
- **Файлы:** `src/lib/cloud-quotas/{contracts,services,index}.ts`, `adapters/monitoring-client.ts` (raw REST через `fetch`, **не** `googleapis`-клиент — тот же паттерн, что `auth.ts`'s `revokeGoogleToken`/`fetchGoogleIdentity`, поэтому `read-gateway-inventory.test.ts` этот модуль не затрагивает вообще). Google Cloud Project Number извлекается из уже существующего `GOOGLE_CLIENT_ID` (`deriveGoogleCloudProjectNumber`, формат `{project_number}-{random}.apps.googleusercontent.com` — по прямому указанию владельца: «он уже зашит в GOOGLE_CLIENT_ID»), отдельный проектный ID/номер в конфиге не требуется. Встроено в `GET /api/settings`'s `cloudQuotaStatus` (не в отдельный роут — те же компоненты уже читают `/api/settings`). UI: новый переиспользуемый `src/components/progress-bar.tsx` (генерик, без доменной логики) + тонкая обёртка `cloud-quota-progress.tsx`, встроены под тумблерами `ReadGatewaySettings` (Data API reads и Analytics reads по отдельности) и `LiveWritesSettings` (Live writes — тот же счётчик, что Data API reads, по инструкции владельца).
- **Найденный и исправленный баг (до коммита):** первая живая проверка показала `analytics: null` для Analytics API, хотя разведка ранее нашла реальные данные. Причина — `quota/limit` не является постоянным heartbeat-метриком: Google пишет свежую точку только при реальном трафике к сервису, а Analytics API вызывается редко; окно поиска в 1 час часто оказывалось пустым. Исправлено расширением окна до 25 часов (`fetchDailyQuotaLimit`).
- **Деградация:** любая ошибка одного сервиса (или отсутствие Cloud-подключения) даёт `null` для этого сервиса, не бросает исключение и не показывает выдуманный 0 — Settings-таб никогда не падает из-за внешнего API.
- **Свой счётчик трафика (добавлено 2026-09-22, owner instruction: «на него нам нужно повесить такие же счетчики, как на другие API. Он сделан по такой же схеме модуля / шлюза?»):** пятая категория `cloud_monitoring_reads` в `GatewayTrafficCategory` (`src/lib/db.ts`) — каждый реальный вызов из `adapters/monitoring-client.ts`'s единственной choke-point функции `callMonitoring` пишет событие (только `allowed`, тумблера включения/выключения для этой категории нет). UI — тот же `GatewayTrafficStats`, встроен в карточку "Google Cloud connection". **Механически зафиксировано** новым `cloud-quotas-inventory.test.ts` (строковая проверка на URL `https://monitoring.googleapis.com` вне `monitoring-client.ts`, не на голое имя хоста — `contracts.ts`/`services.ts` легитимно используют `"monitoring.googleapis.com"` как значение параметра/типа; `googleapis`-импорта тут вообще нет, поэтому `read-gateway-inventory.test.ts`'s собственная проверка сюда не применима).
- **Третья карточка квоты, поминутная, не суточная (добавлено 2026-09-22, owner: «Не вижу прогресс бара у Google Cloud connection»):** `CloudQuotaStatus` получил третье поле `monitoring` — тип `PerMinuteQuotaStatus` (`{limit, usedLastMinute}`), не `ServiceQuotaStatus`. Живой проверкой найдено: у Cloud Monitoring API в этом проекте нет дневного лимита вообще, только поминутные (`DefaultRequestsPerMinutePerUser` — фактически безлимитный; `QueryRequestsPerMinutePerProject` — реальные 6000/мин, подтверждено). `fetchPerMinuteQuotaLimit`/`fetchLatestMinuteUsage` — отдельные функции (не переиспользуют дневные), берут САМУЮ ПОСЛЕДНЮЮ 1-минутную DELTA-точку (не сумму за 24ч — иначе сравнение с поминутным лимитом всегда показывало бы "превышение"). UI — отдельный компонент `CloudQuotaProgressPerMinute` (не общий `CloudQuotaProgress`), с меткой "per minute" вместо "24h" и фиолетовым (indigo) акцентом вместо красного — тот же цвет, что у кнопки "Connect Google Cloud"/"Save / Apply" (owner instruction).
- **Чего явно нет:** отдельного роута/кэширования (реальный вызов Monitoring API идёт на каждую загрузку Settings-таба — 4 запроса, не оптимизировано); Cloud Quotas API вообще не используется (сознательно, не нужен).

### 2.9ap2 Облачные API вместе: одна вкладка, карточка Gemini в «Серверах», общие расходы и лимиты, один файл ключей (BL-193, ADR 0039) — **IMPLEMENTED на `feature/bl-193-cloud-api-costs`, не влито в `dev`**

- **Настройки:** одна под-вкладка `cloud-apis` («Облачные API»): карточка RunPod (+S3), ключ Gemini, генерация и лимиты Gemini, карточка «Перенести облачные ключи на другой компьютер»; `/settings/runpod` и `/settings/gemini` — страницы-редиректы.
- **«Серверы → Сессии»:** карточка Gemini (`gemini-servers-card.tsx`, свой `FeatureErrorBoundary`): задания этого компьютера со стоимостью или оценкой (≈), расход сегодня/за месяц против лимитов с долей других компьютеров; без баланса (у Google его нет). В шапке — «Gemini сегодня» и расход RunPod по всему аккаунту (`accountSpentTodayUsd`, доля этого компьютера).
- **RunPod:** `getLimits` → `accountSpentTodayUsd`/`otherDevicesSpentTodayUsd` из отчётов `media-sessions` (без списка подов); `spentTodayUsd` — по-прежнему этот компьютер. Agent API 3.19.0.
- **Gemini, расход:** семья sync-gateway `gemini-spend` (`ytm-gemini-spend` v1: сегодня/месяц, отпечаток ключа `HMAC-SHA256("ytm/gemini-key-fingerprint/v1", key)[0..32]`); публикует `gemini-media` (`publishSpendShare`, цикл 30 с в `instrumentation.ts`); `gemini-media/account.ts` суммирует компьютеры с тем же отпечатком (сегодня — с местной полуночи, месяц — с 1-го); `createJob` проверяет лимиты дня и месяца по сумме. Factory API 1.19.0 (`spend.account`).
- **Gemini, лимиты:** семья `gemini-settings` — движок `media-settings` на своём документе (`ytm-gemini-settings`); правила в `gemini-media/settings-sync.ts` (четыре лимита, переключатель не общий); конфликты — в стартовом окне группой «Лимиты Gemini», `GET /api/gemini-media/settings-sync`, `POST .../resolve`.
- **Ключи:** общий модуль `src/lib/cloud-credentials-transfer/` (файл `ytm-cloud-credentials` v1; старый `ytm-runpod-credentials` импортируется); разделы — публичные функции `media-generation` и `gemini-media`; `POST /api/cloud-credentials/export|import`; старые маршруты `media-generation/credentials/export|import` удалены.
