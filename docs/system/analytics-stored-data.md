### 2.9ad Вехи 7-го и 28-го дня по своим роликам (BL-166, FO-REQ-0015 пункты 1 и 8, `docs/roadmap/plans/VIDEO_MILESTONES_PLAN.md`, ADR 0034 Amendment 2) — **IMPLEMENTED, на ветке `feature/fo-req-0015-milestones`**

- **Сбор (`src/lib/analytics/milestones.ts`):** окно вехи — от даты публикации (по Тихоокеанскому времени, как вся Analytics) до +6 / +27 дней; веха собирается через 3 дня после конца окна. Два запроса Analytics API на веху: кривая удержания (`elapsedVideoTimeRatio`, 100 точек, `audienceWatchRatio` и `relativeRetentionPerformance`; с тремя доп. метриками YouTube отвечает пустым ответом — проверено вживую 2026-10-10, v76 удаляет собранные без кривой вехи, чтобы собрать заново) и итоги окна без измерения (views, estimatedMinutesWatched, averageViewDuration, averageViewPercentage). Только публичные ролики (пока ролик приватный или запланирован, YouTube отдаёт владельцу как `publishedAt` время загрузки); веха, собранная для другого окна (дата публикации сменилась), собирается заново, попытки с 1. Не больше 25 вех на канал за проход, сначала старые; попытку засчитывает только ошибка самого запроса (400, 404, «свой» 403) — +1, через сутки повтор, после 3 попыток `failed`; выключенное чтение, квота, вход, 401 и системные 403 останавливают проход без записи; нет ответа сети, 429 и 5xx тоже останавливают, но эта веха откладывается на сутки без попытки (`deferVideoMilestone`), чтобы один ролик не держал очередь канала. Запускается после фонового сбора Analytics (`/api/analytics/auto-collect-all`), с тем же резервом квоты.
- **Хранение:** таблица `video_milestones` (v75, ключ ролик + веха), `authorized` (III.E.4.b), только на этом устройстве (не в снимке и не в синхронизации). Значения — как вернул YouTube; ничего не вычисляется из кривой.
- **Чтение:** `agent_get_video_milestones` (Agent API 3.9.0, возможность `analytics.query_video_milestones`, READ, только канал сессии) — вехи с кривой и длиной ролика; у Producer (API 1.2.0) — он же и `producer_upload_milestones`: ролики всех каналов за период до 92 дней (по UTC-дате, как в портфеле) с итогами 7/28 дней, статусом (`collected`/`retry`/`failed`/`due`/`not_due`) и Reach за то же окно (`getVideoWindowsReach` в `reach-reports`: одно чтение на канал, CTR взвешен по показам; нет дня Reach в окне — `null`). Сборка — `src/lib/portfolio-overview/upload-milestones.ts`, реальная проводка сессии Producer — `src/lib/producer-mcp-endpoint/session-deps.ts`.

### 2.9ae Источники трафика и устройства по дням — хранятся (BL-168, FO-REQ-0015 пункт 2, `docs/roadmap/plans/VIDEO_BREAKDOWNS_PLAN.md`, ADR 0034 Amendment 3) — **IMPLEMENTED, влито в `dev` (`2f98796`)**

- **Сбор (`src/lib/analytics/breakdowns.ts`):** субъекты — канал целиком и каждый публичный ролик (правило `hasFinalPublishDate` из вех) в первые 90 дней после публикации (тихоокеанская дата публикации .. +89). Два запроса Analytics API на субъект: `day,insightTrafficSourceType` и `day,deviceType`, метрики `views` и `estimatedMinutesWatched` (с фильтром `video==` для ролика; проверено вживую 2026-10-10). Последний день — вчера (по Тихоокеанскому времени). Первый сбор — весь диапазон (канал — 90 дней назад от последнего дня); дальше раз в сутки, пока есть новый день: с 6 дней до первого нового дня (последние сохранённые, ещё предварительные дни перечитываются, пропуск заполняется); ролик после конца окна — ещё один проход на конец окна + 7 и больше никогда. Ответ заменяет строки субъекта в прочитанном диапазоне одной атомарной пачкой (при первом сборе — все строки субъекта). Не больше 100 субъектов на канал за проход: канал, затем ролики, давно не собранные первыми (никогда не собранные — первыми, среди равных — новее), так что пропущенный ролик идёт первым в следующий проход (ревью BL-168: при 50 и порядке «от новых к старым» старые ролики окна выпадали каждый день); пачка выбирается только по этому порядку, а внутри неё субъекты в `retry` (и канал) идут последними: ролик без ответа YouTube, останавливающий проход, не мешает читать остальные, и при этом не вытесняется из пачки навсегда. Ошибки — по правилам вех (`query-failure.ts`, общий файл): стоп без записи, отложить на сутки без попытки, попытка (у ролика 3 — `failed`; канал не сдаётся никогда, повтор через сутки). Запускается в `/api/analytics/auto-collect-all` после вех, с тем же резервом квоты и меткой истории квоты.
- **Хранение (v77):** `video_breakdown_daily` (ролик, разбивка, день, значение; канал, просмотры, минуты), `channel_breakdown_daily` (то же для канала), `analytics_breakdown_state` (канал + субъект `channel`/id ролика: начало диапазона, сохранено по, дата и время сбора, статус, попытки). `authorized` (III.E.4.b), только на этом устройстве (не в снимке и не в обмене `analytics-data`: формат файлов строгий, версия 1).
- **Чтение:** `agent_get_stored_breakdowns` (Agent API 3.10.0, возможность `analytics.query_stored_breakdowns`, READ, только канал сессии; у Producer — в закрытом списке, Producer API 1.3.0) — канал или до 20 роликов, до 92 дней, суммы по значению (`total`) или строки по дням (`day`), `coverage`, статус, сырое значение API и метка. Вкладка Analytics по-прежнему читает свои карточки вживую.

### 2.9af Поисковые запросы по роликам и неделям канала — хранятся (BL-169, FO-REQ-0015 пункт 5, `docs/roadmap/plans/VIDEO_SEARCH_TERMS_PLAN.md`, ADR 0034 Amendment 4) — **IMPLEMENTED, влито в `dev` (`30ce7bc`)**

- **Сбор (`src/lib/analytics/search-terms.ts`):** те же ролики и окно 90 дней, что в §2.9ae. Один запрос Analytics API на ролик: `insightTrafficSourceDetail` с фильтром `video==<id>;insightTrafficSourceType==YT_SEARCH`, метрики `views` и `estimatedMinutesWatched`, `maxResults=25` и `sort=-views` (оба обязательны, больше 25 YouTube не отдаёт; разбивки по дням нет; проверено вживую 2026-10-10). Каждое чтение — итог за окно до вчерашнего дня, он целиком заменяет запросы ролика. Первое чтение, когда у ролика есть 7 дней, дальше раз в 7 дней; после конца окна — одно чтение на конец окна + 7. Не больше 100 запросов на канал за запуск, сначала давно не читанные; правила ошибок общие (`query-failure.ts`). **Недели канала** (по решению владельца, Telegram msg 2477): тот же запрос без `video==`, за каждую неделю пн–вс (тихоокеанские даты), последние 13 полных недель; неделя читается, когда закончилась, и ещё раз на воскресенье + 7. В запуске сначала недели, потом ролики. Запускается после разбивок в `/api/analytics/auto-collect-all`; шлюз чтения передаёт `maxResults` и `sort`.
- **Хранение (v78):** `video_search_terms` (ролик, запрос; канал, просмотры, минуты), `channel_search_terms_weekly` (канал, понедельник, запрос; просмотры, минуты); состояние — в `analytics_breakdown_state` под `search:<id ролика>` и `search-week:<понедельник>`. `authorized`, только на этом устройстве.
- **Чтение:** `agent_get_stored_search_terms` (Agent API 3.11.0, возможность `analytics.query_stored_search_terms`, READ, только канал сессии; у Producer — в закрытом списке, Producer API 1.4.0) — до 20 роликов (окно, `coverage`, статус и до 25 запросов) или недели канала за период до 92 дней (суммы по запросу — `total`, или по неделям — `week`). YouTube называет запрос лишь для части поисковых просмотров (на наших каналах в октябре 2026 — около 12–20%). Неделя без ответа YouTube останавливает только недели этого запуска, ролики читаются дальше (ревью BL-169).

### 2.9ap Источники «Рекомендуемые видео» по роликам и неделям канала — хранятся (BL-191, FO-REQ-0026 / PRD-REQ-0013, `docs/roadmap/plans/SUGGESTED_SOURCES_PLAN.md`, ADR 0034 Amendment 7) — **IMPLEMENTED, влито в `dev` (`f5fe622`)**

- **Общий модуль (`src/lib/analytics/traffic-source-details.ts`):** расписание, цикл сбора и форма чтения §2.9af вынесены сюда с параметром источника (`YT_SEARCH` / `RELATED_VIDEO`) и префиксами состояний; `search-terms.ts` — его конфигурация `YT_SEARCH` (имена и ответ BL-169 не менялись), `suggested-sources.ts` — `RELATED_VIDEO`.
- **Сбор:** те же ролики, окно, недели, лимит 100 и правила ошибок, что в §2.9af, фильтр `insightTrafficSourceType==RELATED_VIDEO`; состояние — `suggested:<id ролика>` и `suggested-week:<понедельник>` (не пересекается с поисковыми). Шаг в `/api/analytics/auto-collect-all` после поисковых запросов. После прохода — названия и каналы чужих рекомендующих видео без названия: `getPublicVideoTitles` в шлюзе чтения (`videos.list`, `snippet`, по 50 id), не больше 500 id за проход, только в резерве Data API; ошибка не ломает сбор; id, который YouTube не вернул, записывается без названия.
- **Хранение (v94):** `video_suggested_sources`, `channel_suggested_sources_weekly` (`authorized`); `suggested_video_titles` (`non_authorized`, часы `fetched_at`: очистка через 30 дней, чтение старше 30 дней не отдаёт). Всё только на этом устройстве.
- **Чтение:** `agent_get_stored_suggested_sources` (Agent API 3.18.0, возможность `analytics.query_stored_suggested_sources`, READ; у Producer — в закрытом списке, Producer API 1.9.0), формы как у поисковых запросов. Строка: `{ videoId, views, estimatedMinutesWatched, source: ours | external, title, channelId, channelTitle }`; `ours` — синхронизированное видео любого канала, подключённого на этом компьютере (название из своих данных), определяется при чтении. Списки неполные (топ-25 на запрос).

### 2.9ah Комментарии к своим роликам — хранятся (BL-171, FO-REQ-0015 пункт 7, `docs/roadmap/plans/VIDEO_COMMENTS_PLAN.md`, ADR 0034 Amendment 6) — **IMPLEMENTED, влито в `dev` (`0fe5183`)**

- **Сбор (`src/lib/video-comments/`, свой модуль):** раз в тихоокеанские сутки на канал — свежие счётчики комментариев неприватных роликов (`getVideoCommentCounts`, `videos.list` statistics, 1 единица на 50; хранимые счётчики фонового канала обновляются только его синхронизацией), затем ролики с комментариями: никогда не читанные, при изменении счётчика или раз в 7 дней (`disabled`/`failed` — только при изменении). Чтение — `listOwnVideoComments` (`commentThreads.list`, 100 новых верхнеуровневых, plain text); пометку «ответ самого канала» шлюз считает сам, данные авторов дальше не идут. Не больше 50 роликов за запуск. Запускается после шагов аналитики в `/api/analytics/auto-collect-all` (те же каналы), за резервом квоты Data API, метка «Comment collection». Правила сбоев — общие, теперь в шлюзе чтения (`read-failure.ts`); 403 `commentsDisabled` — статус `disabled`.
- **Хранение (v80):** `video_comments` (без данных авторов; новый вид политики `authorized_expiring`, III.E.4.c — очистка удаляет строки старше 30 дней по `fetched_at`, в базе, при импорте и в копиях), `video_comment_state`, `video_comment_channel_state`. Только на этом устройстве.
- **Чтение:** `agent_get_video_comments` (Agent API 3.13.0, `video_context.query_video_comments`; у Producer — API 1.6.0).
