### 2.9h Automerge draft layer + multi-device sync (`src/lib/sync-gateway/change-drafts/`, `src/lib/sync-gateway/change-drafts-sync/`, CD1–CD7) — **IMPLEMENTED for the scope below**

- **Перенесено под единый модуль `src/lib/sync-gateway/` 2026-09-22** (owner instruction: "используем также правило 1 модуля и шлюза" — тот же single-gateway-принцип, что и `youtube-read-gateway`/`youtube-write-gateway`, `docs/decisions/0005`/`0007`). Это чистый перенос директорий (`change-drafts` и `change-drafts-sync` стали дочерними модулями `sync-gateway/`, ни одна строка их логики не менялась), M1 из `docs/roadmap/plans/FULL_DEVICE_HANDOFF_MIGRATION_PLAN.md`. Каждый внешний вызывающий код теперь импортирует только барель `@/lib/sync-gateway`, никогда дочерний модуль напрямую — механически проверяется `sync-gateway-inventory.test.ts`. Весь текст ниже описывает работу CD1–CD7 как она была построена (пути в прозе обновлены на новое расположение, поведение не изменилось).
- **Ответственность:** `src/lib/sync-gateway/change-drafts/` — один Automerge-документ на канал (`AUTOMERGE_MIGRATION_PLAN.md` §5), являющийся источником истины для `change_sets`/`changes` (см. §2.9's cutover-заметку); `src/lib/sync-gateway/change-drafts-sync/` (CD5, 2026-09-21) — файловый цикл синхронизации этого документа между устройствами через операторский Syncthing-каталог, переиспользующий существующий `src/lib/bootstrap-config/` (`deviceId`, `syncthingRootPath`) вместо создания второй концепции идентичности устройства.
- **Файлы `sync-gateway/change-drafts/`:** `{contracts,schemas,services,index}.ts`, `adapters/{automerge-store,sql-source,sql-projection,logger}.ts`. Ключевые операции сервиса: `createChangeSet`/`addChange`/`createChangeSetWithChanges` (batched, одна `Automerge.change`+`saveDocument` на всю пачку — атомарность, эквивалентная старому `db.transaction`), `updateProposedValue`/`setApprovalStatus`/`setChangeSetStatus`/`patchChange`/`bulkPatchChanges` (тоже batched), `mergeIncoming`, `listConflicts`, `exportBytes`, `migrateFromSql` (одноразовая, CD4). `adapters/automerge-store.ts`'s `saveDocumentBytes` пишет через temp-файл + атомарный `rename`, никогда напрямую — крах посреди записи не может оставить повреждённый, незагружаемый `.automerge`-файл.
- **`mergeIncoming`'s две эмпирически найденные и исправленные защиты от тихой порчи данных (обе — до появления любого production-кода, использующего множественные устройства):** (1) если у устройства ещё нет локального документа для канала, входящие байты пира принимаются напрямую (`Automerge.load`), а не мержатся в свежесозданный `emptyDocument()` — иначе `Automerge.merge()` между двумя независимо созданными документами терял ВЕСЬ документ пира в 55% прогонов (измерено эмпирически, не редкий краевой случай); (2) если у устройства УЖЕ есть документ, но он не имеет общей истории с входящим (например, оба независимо бутстрапнулись через `migrateFromSql` без предварительной синхронизации), `mergeIncoming` явно отказывает кодом `divergent_document_lineage` (сравнение `genesisChangeHash` — хеша самого первого change документа) вместо тихой потери данных — при таком сценарии потеря была ДЕТЕРМИНИРОВАННОЙ (100/100), а не вероятностной. Оба случая — постоянные регрессионные тесты в `services.test.ts`, не одноразовые скрипты. **RISK-46, частично исправлено 2026-09-22:** новый `discardLocalAndAdoptPeer({channelId, incomingBytes})` — явное, инициируемое человеком (никогда не автоматическое) "отбросить локальную копию, принять версию пира", с обязательным бэкапом отбрасываемого документа перед перезаписью (`adapters/discarded-backup-store.ts`, отдельный от `src/lib/backup/` из-за несовместимой per-video формы последнего). `sync-gateway/change-drafts-sync/services.ts`'s `adoptDivergentPeer({channelId, peerDeviceId})` заново читает АКТУАЛЬНЫЙ файл пира из папки синка в момент разрешения (а не кэшированные байты из старого цикла) и взаимно исключается с `runSyncCycle` (каждый дожидается in-flight вызова другого, не коалесируясь с ним). UI: кнопка "Discard my local copy, adopt this device's version" появляется только для `peersSkipped`-записей с `reason === "divergent_document_lineage"` активного канала, за `ConfirmDialog`. **Живьём найденный и исправленный баг:** `saveDocument`'s проекция только апсертит текущие строки документа, никогда не удаляет строку для changeSet/change, существовавшего ТОЛЬКО в отброшенном документе — без фикса такая строка навсегда оставалась видимой через `listChangeSets`, но кидала `not_found` при любом действии над ней. Исправлено новыми `deleteStoredChangeSet`/`deleteStoredChange` (`db.ts`) и `deleteChangeSet`/`deleteChange` (`SqlProjectionAdapter`) — `discardLocalAndAdoptPeer` считает разницу ключей отброшенного и принятого документов и удаляет только то, что реально исчезло. **Не исправлено:** вариант (a) — структурное предотвращение самого расхождения (это только уборка ПОСЛЕ того как оно уже произошло).
- **Файлы `sync-gateway/change-drafts-sync/`:** `{contracts,services,index}.ts`, `adapters/filesystem-transport.ts`. Каждое устройство пишет ТОЛЬКО свой собственный файл — `<syncthingRootPath ?? локальный fallback>/change-drafts/<channelId>/<deviceId>.automerge` (санитизированные имена), никогда общее на несколько устройств имя, поэтому generic same-filename-конфликт Syncthing для этих данных структурно не возникает; `listPeerFiles` строго фильтрует имена файлов (`^[a-zA-Z0-9_-]+\.automerge$`), исключая как собственный файл устройства, так и артефакты самого Syncthing (`.sync-conflict-*`, `.syncthing.*.tmp`) — ни один из них никогда не передаётся в `Automerge.load`. Один цикл синхронизации (`runSyncCycle`) для каждого известного локально канала: (a) экспортирует и пишет локальный документ (если он есть — канал без него просто пропускает push, это не ошибка), (b) читает все файлы пиров, кроме своего, (c) мержит каждый по отдельности, изолируя одну плохую/повреждённую/разошедшуюся запись от остальных (одна ошибка пира не прерывает синк остальных каналов/пиров — `peersSkipped`, отдельно от обычных `FieldConflict`). **Push происходит ДО pull-мержа** — смёрженное на этом цикле состояние публикуется пирам только на следующем цикле (сходится за 2 цикла, не за 1 — учитывать в UI CD6, кнопка "Sync now" не публикует мгновенно оба направления). **Single-flight guard**: `runSyncCycle()` — не более одного цикла одновременно на один экземпляр ядра; поэтому `createChangeDraftsSyncCoreForProduction()` в `index.ts` **мемоизирован** (единственный экземпляр на процесс), в отличие от `sync-gateway/change-drafts/index.ts`'s собственного stateless `createChangeDraftsCoreForProduction()` — иначе гвард был бы no-op при типичном для этого проекта паттерне «фабрика ядра внутри каждого обработчика роута».
- **CD6 (первый слайс, 2026-09-21) — проводка + минимальный UI.** Три новых API-роута: `POST /api/change-drafts/sync` (device-wide, запускает `runSyncCycle()` — гейтится `src/proxy.ts`'s device-availability lock как любая другая мутация, поскольку не в списке исключений), `GET /api/change-drafts/conflicts-summary` (device-wide, дешёвый — суммирует `listConflicts` по каждому локально известному каналу, БЕЗ записи), `GET /api/channels/[channelId]/change-drafts/conflicts` (per-channel, с `channelAccess.assertActiveChannel`, для детального списка конфликтов активного канала). Оба device-wide роута не берут `channelId` от клиента (список каналов — `listStoredChannels()`, серверная сторона), поэтому §6.6(b)'s active-channel проверка к ним не применяется — по аналогии с `src/app/api/device-handoff/**`. Вкладка "Device" переименована в **"Merge"** (`src/app/dashboard/page.tsx`); `src/components/device-handoff-panel.tsx` получил новую секцию "Change drafts sync" (кнопка "Sync now" + список текущих `FieldConflict` для активного канала, N-колоночный дифф по `valuesByActor`, аналог `change-set-review.tsx`'s 2-колоночного паттерна). Опрос с фронтенда (`page.tsx`) — два независимых интервала: дешёвый `conflicts-summary` каждые 20с (для бейджа в сайдбаре — badge живёт на самом nav-элементе "Merge" через новое поле `NavItem.badge`, не в отдельной header-иконке, которой пока нет ни для чего другого) и настоящий sync-цикл (`POST .../sync`) каждые 60с — оба независимы от того, какая вкладка открыта, обеспечивая AC-CRDT-07 (фоновая синхронизация без необходимости открывать Merge). **Явно НЕ реализовано в этом слайсе:** сама возможность "разрешить" конфликт (выбрать одну из конкурирующих версий) — UI только показывает конфликты, разрешение — следующий подслайс. **Живая проверка** (реальный канал Tropico Jazz, `claude-in-chrome`): "Sync now" реально экспортировал и записал `.automerge`-файл в настоящую Syncthing-папку на внешнем диске (`/Volumes/Samsung T9/YouTube/YT Manager Data/change-drafts/<channelId>/<deviceId>.automerge`), подтверждён валидный загружаемый Automerge-документ; бейдж в сайдбаре корректно показал "3" при временно застабленном ответе и корректно вернулся к пустому состоянию после перезагрузки; ноль ошибок в консоли. Настоящий CRDT-конфликт через UI живьём не демонстрировался (создание искусственного конкурентного редактирования того же документа оказалось не тривиальным без порчи реальных данных) — рендеринг блока конфликтов проверен только на пути "конфликтов нет"; сам механизм обнаружения конфликтов уже покрыт исчерпывающими модульными тестами (`sync-gateway/change-drafts/services.test.ts`'s AC-CRDT-02 и смежные).
- **Read/Write:** ноль вызовов YouTube API во всех трёх модулях; вся запись — в локальный `.automerge`-файл устройства и в файлы обмена в Syncthing-каталоге (если он настроен) либо в локальный fallback-каталог (`changeDraftsSyncFallbackDir`, `src/lib/platform-paths/`).
- **Важное ограничение безопасности:** `channelId` внутри Automerge-документа — удобство партиционирования данных, никогда не решение об авторизации; `write-context.assertWriteChannel` остаётся единственным источником истины для того, на какой канал разрешена запись (AC-CRDT-06, `AUTOMERGE_MIGRATION_PLAN.md` §5).
- **CD6 (второй подслайс, 2026-09-21) — разрешение конфликтов.** Новый метод `sync-gateway/change-drafts/services.ts`'s `resolveConflict({channelId, changeId, field, winningActorId})`: принимает `winningActorId`, НЕ сырое значение — реальное побеждающее значение переизвлекается сервером через `Automerge.getConflicts`, поэтому в документ никогда не может попасть значение, которое не было одним из уже легитимно конфликтующих (записанных через собственные валидированные пути этого модуля). Ограничен полями `proposedValue`/`approvalStatus`/`approvedValue`/`conflictStatus` — единственными, на которых два устройства реалистично могут конфликтовать (`baselineValue`/`changeType`/`validationStatus` выставляются один раз при создании и никогда не редактируются повторно через API этого модуля). Эмпирически подтверждено (пробный скрипт, не из документации Automerge): свежая запись `Automerge.change` поверх конфликтующего поля полностью снимает конфликт (`getConflicts` возвращает `undefined`) и переживает границу save/load. `POST /api/channels/[channelId]/change-drafts/conflicts` — новый обработчик в том же файле, что и `GET` для списка конфликтов; реальная мутация, гейтится `src/proxy.ts` как любая другая запись. UI: кнопка "Use this version" под каждым конкурирующим значением в `device-handoff-panel.tsx`, подтверждение через `ConfirmDialog` (BL-043's стандартное правило для необратимых действий), после подтверждения — обновление списка конфликтов. Поле, не входящее в разрешаемый набор, по-прежнему отображается (никогда не скрывается), но без кнопки действия и с явной пометкой "can't be resolved from this screen yet". **Живьём проверено против реального Tropico Jazz** (advisor: "near-free" раз сервер всё равно поднимался ради проверки исправлений push-изоляции): создан одноразовый тестовый Change Set, затем сконструирован НАСТОЯЩИЙ конкурентный конфликт (форк реального документа в поддельный peer-файл + независимое редактирование того же поля через настоящий production `change-drafts` core) — "Sync now" корректно показал "1 new conflict(s)", карточка конфликта отрисовала оба значения, клик "Use this version" по значению локального устройства реально записал выбранное значение (подтверждено прямым чтением файла на диске после клика), список конфликтов и бейдж в сайдбаре корректно очистились после следующего опроса. Ноль ошибок в консоли. Тестовые артефакты (поддельный peer-файл, тестовый Change Set) удалены/отклонены после проверки.

- **Статус:** `docs/roadmap/plans/FULL_DEVICE_HANDOFF_MIGRATION_PLAN.md`, слайсы M0-M4 и M6 — все DONE, смержены в `dev` 2026-09-23 (`docs/ROADMAP_STATUS.md`, `docs/roadmap/BACKLOG.md` BL-064..BL-068). M5 (Category D: `batches`/`batch_ledger_rows`/`batch_attempts`/`audit_events`) отменён целиком, см. `docs/decisions/0009-defer-write-pipeline-sync-gateway-migration.md`.
- **Общий движок `src/lib/sync-gateway/automerge-core/`** (`{store,engine,transport,sync-runner,index}.ts`) — вынесенная из §2.9h's `change-drafts` document-shape-agnostic часть проверенной CD1-CD7 merge-логики, переиспользуемая новыми каталогами БЕЗ изменения уже отгруженного `change-drafts/`. Ключевой найденный и исправленный баг: `Automerge.merge(before, incoming)` мутирует свой первый аргумент на месте — сканирование "before"-состояния ПОСЛЕ вызова `merge` тихо теряло реальные конфликты; `mergeIncoming` теперь принимает callback `scanConflicts` и всегда сканирует "before" до вызова `Automerge.merge`. BL-270: `store.saveDocumentBytes` и `transport.writeDeviceFile` не перезаписывают файл с теми же байтами (`writeFileAtomicIfChanged`; так же per-device-report `writeLocal`/`writePeer`) — неизменённый документ больше не получает свежий mtime и fsync каждую минуту.
- **`src/lib/sync-gateway/editorial-profile/` + `editorial-profile-sync/` (M3, часть 1)** — реальный per-channel документ (плоский объект, `version: number`, `0` = "никогда не сохранялся" — sentinel для bootstrap из существующей SQL-строки при первом сохранении, без потери данных). Cutover: `src/lib/ai-localization/adapters/profile-store.ts`.
- **`src/lib/sync-gateway/ai-connections-catalog/` + `ai-connections-catalog-sync/` (M3, часть 2)** — ЕДИНЫЙ глобальный документ (не per-channel — у `ai_connections` нет `channel_id`), ключ — константа `GLOBAL_DOCUMENT_KEY = "global"`, переиспользующий тот же generic per-channel `sync-runner` через одноэлементный `listChannelIds: async () => ["global"]`. Cutover: `src/lib/ai-connections/adapters/store.ts`. **Живьём найденный и дважды исправленный orphan-row баг** (тот же класс, что RISK-46 в `change-drafts`): при удалении соединения пиром "touched ids" для SQL-проекции нужно считать объединением ключей ДО и ПОСЛЕ merge, а не только "после" — иначе `deleteConnection` для удалённого пиром соединения никогда не вызывается. Исправлено в `mergeIncoming` И в `discardLocalAndAdoptPeer` независимо (оба места ранее имели один и тот же пробел).
- **M4 — `ai_localization_generation_provenance` внутри `change-drafts`.** Аддитивное опциональное поле `provenance?: Record<string, DraftProvenance>` на существующем per-channel документе (§2.9h) — документ, сохранённый до M4, просто не имеет этого ключа; каждое чтение защищено (`if (!draft.provenance) draft.provenance = {}`). **Найденный и дважды исправленный (независимым ревью, затем повторной проверкой через advisor-инструмент) баг в `discardLocalAndAdoptPeer`:** `ai_localization_generation_provenance.change_set_id` — реальный `NOT NULL UNIQUE REFERENCES change_sets(id)` без `ON DELETE`, при `foreign_keys=ON`; удаление отброшенного change set с provenance-строкой падало на constraint, и это тихо прерывало очистку ВСЕХ остальных строк того же discard целиком (один `try/catch` на оба цикла). Первый фикс scoped очистку provenance по родительскому change set — тоже неполно (change set может пережить discard у peer'а без provenance для него). Финально: provenance диффится по СОБСТВЕННОМУ набору ключей, как `changes`, независимо от судьбы родительского change set; каждая отдельная попытка удаления — в своём `try/catch`.
- **M6 (2026-09-23) — сужение старого whole-DB `snapshot`/`device-handoff`, а не удаление, см. `docs/ARCHITECTURE.md` §13.5.** `SNAPSHOT_TRANSFERRED_TABLES` теперь = `schema_meta` + 4 таблицы Category D; `change_sets`/`changes`/`channel_editorial_profiles`/`ai_localization_generation_provenance`/`ai_connections` больше не путешествуют этим механизмом.

  - `automerge-core/sync-runner.ts` получил обобщённый `adoptDivergentPeer` (перенесён из `change-drafts-sync`'s собственной bespoke реализации, `AGENTS.md` §M) — `editorial-profile`/`ai-connections-catalog` получили его автоматически через общий `createSyncRunner`; `change-drafts-sync` оставлен нетронутым (`AGENTS.md` §D).
  - `editorial-profile/services.ts` и `ai-connections-catalog/services.ts` получили `resolveConflict`, зеркалирующий `change-drafts`'s собственную реализацию (`winningActorId`, значение переизвлекается из `Automerge.getConflicts`, никогда не берётся сырым от клиента).
  - Новые роуты: `GET/POST .../channels/[channelId]/editorial-profile/conflicts`, `POST .../editorial-profile/adopt-peer`, `GET/POST /api/ai-connections/conflicts`, `POST /api/ai-connections/adopt-peer` (последние два — device-wide, без `channelId`).
  - Новая таблица `sync_family_status` (`db.ts`, SCHEMA_MIGRATIONS v12) — постоянный last-sync-outcome (ok/error/когда) на каждое из 3 семейств, в отличие от одноразового абзаца, пропадающего при перезагрузке страницы. `GET /api/change-drafts/sync-status` (read-only); `POST /api/change-drafts/sync` пишет в эту таблицу после каждого из 3 циклов независимо (падение одного семейства не мешает записать статус остальных).
  - `device-handoff-panel.tsx` (вкладка Merge) переписан: постоянная секция "Sync status" (по строке на семейство), единый список "Conflicts" по всем 3 семействам (resolve уходит на правильный роут в зависимости от семейства), единые peer-skipped/divergent-lineage предупреждения, "Device handoff" — отдельная визуально выделенная карточка (владелец: "отдельная карточка") для явной передачи владения 4 таблицами конвейера записи.
  - Живьём проверено (владелец: "делаем можешь для демонстрации сделать тестовые записи") — реальные конфликты созданы напрямую через production core (Automerge fork+merge в памяти, без файлов-подделок на диске), оба показаны и разрешены через реальный UI, тестовые данные убраны через реальные UI-действия сразу после проверки.

### 2.16a Automatic device sync (`src/lib/device-sync/`) — **IMPLEMENTED**, в `dev` (`21bb583`)

- **Ответственность:** серверный планировщик поверх §2.16. Раз в 30 с:
  - экспорт при локальных изменениях — с BL-270 с задержкой: после 90 с без изменений, при непрерывных правках не реже раза в 10 минут, не чаще раза в 60 с; перед перезапуском restart-when-idle и при простое — принудительный экспорт;
  - «есть ли локальные изменения» — по счётчикам изменений (триггеры на переносимых таблицах → `transferred_change_counters`, локальная таблица; её и триггеры создаёт сама синхронизация при работе, без миграции схемы) и `schema_version`; полный отпечаток — только когда они сдвинулись или раз в 10 минут (BL-270); проверки внутри блокировки перед экспортом/импортом — всегда полные;
  - авто-импорт fast-forward снапшота другого устройства, если локально нечего публиковать;
  - ветка другого компьютера с теми же данными, что у собственной головы, записывается как предок, голова и данные не меняются; чистое устройство при нескольких одинаковых ветках импортирует одну (BL-139);
