### 2.9d Video Details (Studio-parity "Details" edit) — **IMPLEMENTED, module + API + Content-tab UI**

- **Статус:** первая в приложении настоящая (не dry-run-only) запись в YouTube из веб-интерфейса. Назначено владельцем проекта через Telegram 2026-09-20, после явного обсуждения рисков (существующий legacy write-путь `video-metadata.apply` молча трогает `localizations` при любой правке — нарушение AGENTS.md §F — и не имеет backup/diff/approval/audit) и явного выбора «Вариант 3: просмотр + реальное сохранение сразу в YouTube». Сначала (по запросу «модуль, который мы свободно сможем использовать позже, включая запись батчем... не перезаписывая всё остальное») реализован как переиспользуемый модуль с partial-patch семантикой без UI; **UI добавлен тем же днём** (BL-031, после «возвращаемся к тому что через контент можно открывать как в студио отдельные видео и менять их по необходимости») — клик по строке видео в Content открывает `src/components/video-details-panel.tsx`. **С 2026-09-21:** открывается не разворачиванием строки таблицы, а в общем модальном окне `src/components/video-detail-modal.tsx` (см. §2.9e) — по требованию владельца проекта («модуль, который может использоваться как в контенте, так и в языках»).
- **Ответственность:** partial-patch редактирование «родных» (не per-language) полей видео — `snippet.{title,description,tags,categoryId,defaultLanguage}`, `status.{privacyStatus,publishAt,license,embeddable,publicStatsViewable,selfDeclaredMadeForKids,containsSyntheticMedia}`, `recordingDetails.recordingDate`. Список полей подтверждён вживую по официальной документации YouTube Data API v3 (не по памяти, проверено 2026-09-20) — `defaultAudioLanguage`, `madeForKids`, весь `contentDetails.*` (включая возрастное/гео-ограничение) читаемы, но не входят в официальный список «settable properties» и намеренно исключены. **Никогда не трогает `localizations`** — структурно (адаптер даже не запрашивает и не может отправить эту часть), не только по соглашению (AGENTS.md §F).
- **Файлы:** `src/lib/video-details/{contracts,schemas,services,index}.ts`, `adapters/{youtube-api,store}.ts`; новые функции добавлены в тогдашний `src/lib/youtube.ts` — read-часть (`getVideoDetailsContext`) с 2026-09-22 живёт в `src/lib/youtube-read-gateway/data-api.ts`, write-часть (`applyVideoDetailsUpdate`, `pickWritableStatusFields`, `pickWritableRecordingDetailsFields`) — в `src/lib/youtube-write-gateway/index.ts` (см. §2.9g); UI — `src/components/video-details-panel.tsx`, интеграция в `content-manager.tsx`; тесты — `data-api.test.ts` (бывший `youtube.test.ts`, расширен), `video-details/{schemas,services}.test.ts` (22 теста в самом модуле, spec-driven по AGENTS.md §L, ожидания посчитаны вручную из официальной документации API, не скопированы с вывода реализации). `npm test`: 554 → 584 суммарно за обе части этой фичи (модуль+API, затем UI+conflict detection).
- **Точки входа:** `GET /api/channels/[channelId]/videos/[videoId]/details` (чистое чтение снапшота, без патча — то, что панель загружает при открытии, без audit-записи), `POST .../details/preview` (read-only diff по патчу, exempt от `src/proxy.ts`'s operation-lock gate, как и другие preview-роуты), `POST .../details/apply` (реальная запись, НЕ exempt — обычный гейт устройства). Все три — через `createVideoDetailsCore()`.
- **Conflict detection (добавлено вместе с UI, 2026-09-20):** `applyFieldsUpdate` принимает опциональный `expectedEtag` — если видео изменилось на YouTube между preview и apply (другой etag), запрос отклоняется с `video_details_conflict` вместо тихого применения патча поверх диффа, который оператор на самом деле не видел. UI всегда передаёт `expectedEtag`, полученный при последнем preview.
- **Partial-patch семантика (владелец: «поменять что-то одно... не перезаписывая всё остальное»):** патч — Zod-объект, где присутствуют только реально изменяемые поля; сервис читает СВЕЖЕЕ текущее состояние видео непосредственно перед записью, мёржит на него только присутствующие в патче поля, и отправляет в `videos.update` только те `part` (`snippet`/`status`/`recordingDetails`), которые патч реально затронул — патч, трогающий только `title`, никогда не отправляет `status` вообще (не может случайно сбросить его гонкой с другим писателем). YouTube API не поддерживает true field-level PATCH — каждая отправленная часть всегда полная (это и обеспечивает «не перезаписывая остальное» на уровне мёржа, не на уровне API).
- **Safety-модель (AGENTS.md §G, минимум для нового write-пути — identity/validation/backup/diff/approval/dry-run/audit/verification), как это реализовано здесь:**
  - identity check — переиспользован `write-context.assertWriteChannel` (не новый guardrail);
  - validation — Zod-схема, включая cross-field правило (`publishAt` требует `privacyStatus: "private"` в том же патче — иначе YouTube отклоняет запрос) и проверку «видео уже опубликовано» (сервисный уровень, по факту `before.publishAt`), а также точный лимит `description` в БАЙТАХ UTF-8 (не JS-символах — эмодзи/кириллица бьют лимит раньше 5000 символов) и бюджет `tags` с учётом запятых/кавычек;
  - backup — переиспользован (не задублирован) `src/lib/backup/` (см. ниже про генерализацию);
  - diff — `previewFieldsUpdate` возвращает before/proposed по каждому полю патча;
  - approval — отдельная явная кнопка «Save to YouTube» в `video-details-panel.tsx`, заблокированная, пока diff не просмотрен для ТОЧНО текущего патча (правка любого поля после preview снова блокирует кнопку — сравнение патчей по значению, не по факту клика);
  - dry-run — `previewFieldsUpdate`, полностью read-only, никогда не вызывает `videos.update`;
  - audit — **новая, отдельная таблица** `video_edit_audit_events` (см. ниже, почему не переиспользован `audit_events`);
  - verification — после записи выполняется НЕЗАВИСИМОЕ повторное чтение видео и сверка каждого патченного поля с тем, что было отправлено; расхождение — `update_failed`, а не тихий успех.
- **Обобщение `src/lib/backup/` (2026-09-20, документированная причина по AGENTS.md §D):** `captureBackup`'s параметр переименован `batchId` → `operationId` (чистое переименование, поведение не изменилось — это был не Batches-специфичный концепт, просто назывался по единственному на тот момент вызывающему); `BackupSnapshot` расширен до discriminated union (`{kind:"localization",...}` — прежнее поведение Batches, `{kind:"video_fields",...}` — новый вариант). Файловый layout (`<root>/<channelId>/<operationId>/<videoId>.metadata_before.json`, атомарный `wx`-флаг против перезаписи) не изменился.
- **Почему audit — ОТДЕЛЬНАЯ новая таблица, а не переиспользование `audit_events`:** `audit_events.batch_id`/`ledger_row_id` — `NOT NULL` FK на `batches`/`batch_ledger_rows`; одиночная правка видео вне Batch не имеет ни того, ни другого id, а ослабление этих `NOT NULL FK` — ровно тот «первый неаддитивный schema change», для которого `docs/decisions/0001-additive-idempotent-schema-strategy.md` требует отдельного ADR, и трогать проверенный Phase 5 audit trail ради этого не нужно. `video_edit_audit_events` (SCHEMA_MIGRATIONS версия 5) — без единого foreign key (осознанно, чтобы append-only лог переживал строку, которую описывает, и не добавлял новых edge для RISK-33's `foreign_keys=ON`), с обычными `channel_id`/`video_id` TEXT-колонками.
- **«Не ломая синхронизацию» (владелец, дословно):** после успешной записи `src/lib/video-details/adapters/store.ts`'s `refreshVideoFields` обновляет ТОЛЬКО те поля локального кэша `videos`, что реально существуют в этой таблице И были затронуты патчем (`title`/`description`/`privacyStatus`/`defaultLanguage`/`etag`) — переиспользуя `upsertVideos` (не новый write-путь), но сначала читая текущую строку через новый `getStoredVideo(channelId, videoId)`, чтобы не обнулить остальные колонки (`upsertVideos` всегда перезаписывает весь ряд целиком). Осознанно **не продвигает** `lastSyncedAt` — это поле означает «случился полный ресинк канала», чем точечная правка одного поля не является; продвижение сломало бы `content-manager.tsx`'s `AUTO_RESYNC_STALENESS_MS`-логику для полей, которые эта правка не трогала (`viewCount`/`commentCount`/`likeCount`, `thumbnails`, `existingLocalizations`).
- **Read/Write:** `previewFieldsUpdate` — только чтение (`YOUTUBE_READ_SCOPE`), ноль вызовов `videos.update`. `applyFieldsUpdate` — единственный настоящий write-путь этого модуля, `YOUTUBE_WRITE_SCOPE`, ровно один вызов `videos.update` на патч, всегда только с реально затронутыми `part`.
- **UI:** `src/components/video-details-panel.tsx`, открывается в общем модальном окне `src/components/video-detail-modal.tsx` (§2.9e) при клике по видео в `content-manager.tsx` (было — разворачивающаяся строка таблицы, заменено 2026-09-21). Основные поля (title/description/privacy/category/tags) видны всегда, остальные — за «Show more». «Preview changes» → diff → «Save to YouTube» становится активной, только если текущий патч байт-в-байт совпадает с тем, что был в последнем preview; любая правка формы после preview снова блокирует кнопку с подсказкой «Preview again before saving».
- **Live-верификация (2026-09-20):** и `preview`/`GET details`-роуты, и вся UI-логика блокировки кнопки «Save to YouTube» проверены вживую в браузере против реального видео канала «Tropico Jazz» — корректный diff, корректные ошибки валидации, корректное блокирование/разблокирование кнопки при правке поля до/после preview. **`apply` ни разу не был вызван ни агентом, ни через UI-клик по «Save to YouTube»** — по явной договорённости с владельцем проекта, первую настоящую запись инициирует только он сам.
- **Чего нет:** CLI/MCP-инструментов (модуль спроектирован для переиспользования, но провода пока нет — тот же RISK-04, что и у остальных доменов); batch-режима (владелец просил «включая запись батчем» — сервисная функция уже per-video и композируема в цикле, но интеграция с Batches' ledger/UI для множественного выбора видео не сделана в этом проходе); поддержки кастомных thumbnail/captions (отдельные YouTube API endpoint'ы, не `videos.update` — не в скоупе этой задачи; позже: обложка — BL-255 `video-thumbnails`, субтитры — BL-269 `video-captions`, §2.9bm); `paidProductPlacementDetails.hasPaidProductPlacement` (документация API неоднозначна насчёт возможности записи — не реализовано, требует эмпирической проверки перед добавлением).

### 2.9e Video detail popup (общий UI-модуль) — **IMPLEMENTED**

- **Добавлено 2026-09-21**, по прямому требованию владельца проекта (Telegram): «Первая правка функционала, может использоваться как в контенте, так и в языках и возможно будет нужна где-то ещё — поэтому можно делать модулем. При нажатии на видео, нам раскрывать информацию о нём не расширением строки, а выводить отдельный поп ап, почти на весь экран... Функционал/наполнение этого поп апа будет отличаться в зависимости от того в какой категории мы сейчас находимся.»
- **Ответственность:** `src/components/video-detail-modal.tsx` — чисто презентационная общая «оболочка» попапа (затемнение фона, near-fullscreen карточка, шапка с миниатюрой/заголовком/кнопкой закрытия, закрытие по клику на фон и по Escape). Не содержит никакой доменной логики и не знает, что именно отображает — контент передаётся вызывающей стороной через `children`, поэтому наполнение осознанно различается по вкладке (в Content — `VideoDetailsPanel`, в Languages — оригинал/локали/инлайн-генерация), как и просил владелец.
- **Используется:** `content-manager.tsx` (заменил разворачивающуюся строку `<tr>`) и `languages-manager.tsx` (аналогично, включая существующий инлайн-генератор AI-переводов, который переехал внутрь попапа без изменения своей внутренней логики). Оба компонента ищут открытое видео по полному (не отфильтрованному/не постраничному) списку, чтобы попап оставался корректным, даже если оператор поменяет поиск/сортировку/страницу, пока он открыт.
- **Точки входа:** нет собственного API — чисто клиентский UI-компонент.
- **Read/Write:** не меняет ничего в контракте данных — под капотом остались те же самые вызовы (`GET .../details`, `GET .../localizations/[videoId]`), что и раньше при разворачивании строки.
- **Правки после первого пользовательского тестирования (тот же день, Telegram):** (1) клик-и-протяжка (выделение текста) внутри попапа, отпущенная за его пределами, раньше засчитывалась как клик по фону и закрывала попап — исправлено: закрытие по клику на фон теперь требует, чтобы И `mousedown`, И `mouseup` произошли непосредственно на самом фоне, а не только `mouseup` (событие `click` в браузере срабатывает по месту `mouseup`, независимо от того, где началось выделение). (2) Если внутри попапа есть несохранённые изменения, попытка закрыть (фон/крестик/Escape) больше не закрывает его сразу — сначала показывается подтверждение «Discard unsaved changes?» (новый проп `hasUnsavedChanges`, `content-manager.tsx` получает его из нового `onDirtyChange`-колбэка `VideoDetailsPanel`, `languages-manager.tsx` — из наличия ещё не отправленных AI-предложений в открытой генерации для этого видео). (3) В Content поле Description увеличено (растягивается на всё оставшееся по высоте место, с собственным скроллом), Tags стало трёхстрочным textarea вместо однострочного поля.
- **Live-верификация (2026-09-21, оба захода):** обе вкладки проверены вживую в браузере против реального канала «Tropico Jazz» — открытие попапа, корректное содержимое (включая генерацию AI-перевода внутри попапа Languages), закрытие кликом по фону и клавишей Escape, устойчивость к клику-и-протяжке за пределы попапа, появление и работа диалога подтверждения при несохранённых изменениях в обеих вкладках. Ноль ошибок в консоли.
- **Чего нет:** ни один другой таб пока не использует этот модуль (Batches, Home и т.д.) — расширение переиспользования оставлено на будущее, когда/если появится такая потребность, как и предвидел владелец («возможно будет нужна где-то ещё»).
- **Общий `ConfirmDialog`, добавлено 2026-09-21 (постоянное правило владельца, `docs/DEVELOPMENT_PLAYBOOK.md` §6.9 п.9): никакие спроектированные нами попапы/предупреждения не должны рендериться нативными диалогами браузера (`window.confirm`/`alert`/`prompt`) — только через собственный UI в едином стиле.** Поводом послужил `window.confirm` в `languages-manager.tsx` (`handleRemoveTrackedLanguage`), который не только не соответствовал стилю приложения, но и (обнаружено в этот же день) блокировал CDP-управляемую браузерную автоматизацию, используемую для живой проверки. Новый `src/components/confirm-dialog.tsx` — единственная реализация (AGENTS.md §D), `fixed inset-0 z-[60]`, работает и как самостоятельный оверлей (Languages), и вложенным в уже открытый `VideoDetailModal` (Content/Languages discard-confirm). Оба существующих `window.confirm` в `languages-manager.tsx` и инлайновый discard-диалог в `video-detail-modal.tsx` переведены на этот компонент; в кодовой базе `grep` не находит больше ни одного `window.confirm/alert/prompt`. Live-проверено в браузере: обе ветки удаления языковой колонки (без реальных данных / с реальными данными) показывают стилизованный диалог вместо системного, without-real-data ветка отработала end-to-end (Cancel/Remove), with-real-data ветка показала полный текст предупреждения и корректно отменяется по Cancel.
- **Languages: двухколоночный редизайн попапа рассмотрения видео, добавлено 2026-09-21 (owner instruction, BL-044).** `VideoDetailModal` получил опциональный `widthClassName` (по умолчанию `max-w-5xl`, Content не затронут) — Languages передаёт `max-w-7xl`. Внутри (`renderVideoLocalizationDetail`): слева — оригинал (defaultLanguage видео, заголовок и описание каждый в своём боксе со своим `overflow-y-auto`); справа — дропдаун выбора языка перевода поверх такого же заголовок+описание бокса. Дропдаун сознательно построен на `overview.languages` (та же уния отслеживаемых/реальных языков, что и колонки таблицы) minus `video.defaultLanguage`, а не на `detail.locales` — значит можно выбрать язык, которого у видео ещё нет, и увидеть пустое состояние с кнопкой «Generate with AI for this language», которая открывает существующую генерацию с уже подставленным целевым языком (`startRowGenerate` + `setTargetLanguages`). Выбор языка сохраняется при переключении между видео (если он ещё валиден для нового видео), сбрасывается на первый доступный иначе. Live-проверено в браузере на канале Tropico Jazz: пустое состояние для "en"/"en-US" (на этом канале ни у одного видео нет кросс-языкового перевода — единственная реальная локализация видео всегда совпадает с его собственным defaultLanguage), заполненное состояние проверено временной подменой `fetch` на синтетические данные (без изменения реальной БД) — оба текстовых блока корректно скроллятся независимо; кнопка генерации по конкретному языку корректно предзаполняет форму.
