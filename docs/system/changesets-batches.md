### 2.9 Change sets / XLSX import / diff & approval (Phase 4) — **IMPLEMENTED** (local-only; real YouTube write remains **PLANNED**, Phase 5)

- **Статус: реализовано как отдельный доменный модуль `src/lib/changesets/`.** Новые таблицы БД (`change_sets`, `changes`), новый парсер XLSX-импорта, чистый (без React/DB) diff-движок, доменные сервисы, API-роуты, UI. **Ни одного вызова `videos.update` или любого другого write-метода YouTube API нигде в модуле** — approve/reject остаются исключительно локальной операцией, YouTube не затрагивается.
- **Cutover на Automerge (2026-09-21, AUTOMERGE_MIGRATION_PLAN.md §6 CD2, `docs/decisions/0006-*.md`):** источником истины для записи теперь является `src/lib/sync-gateway/change-drafts/` (Automerge-документ на канал), а не сама таблица SQLite напрямую — `change_sets`/`changes` становятся регенерируемой read-проекцией этого документа, перестраиваемой после каждой **успешной** записи. Смена реализована исключительно на уровне адаптера (`src/lib/changesets/adapters/change-drafts-store.ts`, подключён в `src/lib/changesets/index.ts`) — `services.ts`, API-роуты, MCP-инструменты и CLI-команды не изменились и продолжают работать через тот же интерфейс стора, что и раньше. Чтение по-прежнему идёт напрямую из SQL. **Проекция НЕ гарантированно синхронна**: `sync-gateway/change-drafts/services.ts`'s `saveDocument` намеренно изолирует ошибку проекции (try/catch, без повторного throw) — если проекция падает, Automerge-документ (источник истины) уже сохранён корректно, но SQL временно отстаёт до следующей успешной записи; в этом окне чтение через `services.ts` может вернуть устаревшие данные, а `updateChange`/`approveChange` для ещё непроецированной записи получит `not_found` (поиск `channelId` по `changeSetId`/`changeId` идёт через ту же SQL-проекцию). Внешнее поведение не изменилось: по-прежнему ни одного вызова YouTube API.
- **Ответственность:** парсинг и валидация загруженного XLSX (совместим с форматом экспорта Phase 3 — `remote_title`/`remote_description` уже были в экспорте с самого начала Phase 3 и служат baseline для conflict detection; Phase 4 лишь добавил необязательный лист `Meta` со `schema_version`/`exported_at`/`channel_id`), сопоставление `video_id`+`language` с синхронизированными данными канала, построение персистентного Change Set из валидных/невалидных строк (unchanged-и-валидные строки не сохраняются, только учитываются в сводке), field-level diff (ADD/MODIFY/UNCHANGED + conflictStatus), детерминированный жизненный цикл Change Set (`in_review`/`approved`/`partially_approved`/`rejected`, вычисляется чистой функцией `computeChangeSetStatus`), локальные approve/reject (одиночные и массовые), ревалидация конфликтов и инвалидация устаревшего approval при каждом чтении/действии.
- **Файлы:** `src/lib/changesets/{contracts,schemas,diff,import,services,index}.ts` (парсинг XLSX-байт в `import.ts` — тонкая обёртка над общим `src/lib/shared-xlsx/`, см. §2.9u), `adapters/store.ts`; UI — `src/components/change-set-review.tsx` (с 2026-09-20 принимает опциональный `onStatusChange`-колбэк, чтобы родитель мог обновить свой собственный, отдельно закэшированный список Change Sets после approve/reject — нужно для статус-based сабтабов в `languages-manager.tsx`) + блок импорта/экспорта в `src/components/languages-manager.tsx` (ранее — `localization-manager.tsx`).
- **Точки входа:** `core.previewImport(...)`, `core.createChangeSetFromImport(...)`, `core.listChangeSets(...)`, `core.getChangeSet(...)`, `core.approveChange(...)`, `core.rejectChange(...)`, `core.approveAllValid(...)`, `core.rejectAllPending(...)` — через `createChangeSetCore()`.
- **Зависимости:** persistence (`getStoredChannel`, `listStoredVideosByChannel` — те же функции, что использует `channel-sync`/`localization`, для получения *текущего* синхронизированного remote-значения), новые CRUD-функции в `src/lib/db.ts` для `change_sets`/`changes`, `exceljs` для парсинга (без вычисления формул — только `cell.result`/текст, импортируемый контент никогда не исполняется).
- **Read/Write:** **ноль вызовов YouTube API** (ни read, ни write) — весь модуль работает поверх уже синхронизированных локальных данных; запись — только в локальные таблицы `change_sets`/`changes`.
- **Важные ограничения безопасности:** blank-ячейка = нет изменения (`docs/PROJECT_SPEC.md` §16); `video_id` — единственный canonical идентификатор, строка с несуществующим/чужим `video_id` отклоняется как невалидная, а лист `Meta.channel_id`, не совпадающий с целевым каналом, блокирует **весь** импорт целиком (защита от импорта книги, экспортированной для другого канала); conflict detection сравнивает baseline экспорта с *последним синхронизированным* remote-значением — **не свежий вызов YouTube API** (задокументированное ограничение, см. `docs/ARCHITECTURE.md` §6.6); approve возможен только для `validationStatus: valid` + `conflictStatus: none`, а ранее выданный approval автоматически инвалидируется, если после ре-синхронизации remote-значение разошлось с baseline (`docs/ARCHITECTURE.md` §6.7). **RISK-47, исправлено 2026-09-21:** approve/approve-all дополнительно отказывают, если на этом `changeId` есть открытый CRDT-level конфликт (`FieldConflict` из `src/lib/sync-gateway/change-drafts/`, отдельная концепция от `conflictStatus` выше) — новая зависимость `crdtConflicts.listConflictedChangeIds(channelId)` в `changesets/services.ts`, реализованная через `change-drafts`'s `listConflicts`; `approveChange` кидает `crdt_conflict_open` (409), `approveAllValid` молча исключает такое изменение из пакета, не проваливая весь батч.
- **Deletion-предложения, добавлено 2026-09-21, backend + UI (`docs/PROJECT_SPEC.md` §16, обновление 2026-09-20 — удаление никогда не мгновенно/безвозвратно).** Новый `ChangeType` `"delete"` и `ChangeSetSource` `"deletion"`; `changesets.proposeLocalizationDeletion({channelId, language, videoIds?})` создаёт Change Set из `delete`-изменений (title+description на видео) для одного языка, проходящий тот же review/approval/conflict-пайплайн, что и любой другой Change Set — это только первый из нескольких обязательных этапов подтверждения, а не само удаление. Опущенный `videoIds` означает «каждое видео канала, у которого есть реальная локализация на этот язык» (bulk/whole-column форма — добавлена E5b поверх исходной single-видео версии); переданный `videoIds` ограничивает предложение конкретным подмножеством. **Жёстко исключает** (не ошибка, а `skippedDefaultLanguageVideoIds` в ответе) любое видео, у которого запрошенный язык — это его собственный `defaultLanguage`: этот язык живёт в `snippet.title`/`description`, а не в удаляемой `localizations`-записи, и `buildSafeLocalizationsPayload` (`src/lib/batches/merge.ts`) в таком случае обнулил бы реальные title/description видео вместо удаления локализации. Это исключение считается напрямую по `video.defaultLanguage`, а не через `existingLocalizations`-объединение (`collectChannelLanguages`) — независимая от последнего проверка обязательна, потому что видео может иметь язык как `defaultLanguage`, не внося вклад в `existingLocalizations` вообще («undercount trap», найдено advisor-ревью). Если после фильтрации не осталось ни одного затронутого видео, функция возвращает `{changeSet: null, ...}` — это не ошибка, а легитимный результат («предлагать нечего»). `buildSafeLocalizationsPayload` дополнен тем же самым guard'ом как defense-in-depth и delete-wins мерж-логикой (удаление применяется после всех остальных изменений батча, поэтому побеждает над одновременным modify той же локали независимо от порядка). **UI (E5b):** кнопка «✕» у языкового заголовка в `languages-manager.tsx`, если у языка есть хотя бы одно реальное видео — вместо тихого untrack показывает явное предупреждение (что произойдёт, что backup уже делается существующим batch-пайплайном подготовки, что ничего не применяется немедленно) и по подтверждению вызывает `POST .../localizations/languages/[language]/propose-deletion` (bulk-форма, без `videoIds`); колонка **намеренно не снимается с отслеживания** при реальном удалении — она и так остаётся видимой через объединение (E5a), пока реальные данные не исчезнут после настоящей записи+ресинка. **Явно НЕ реализовано:** restore-механизм (30-дневное окно локального восстановления из §16) — отложен до реальных live-валидационных тестов Gate B, поскольку до снятия барьера `assertLiveWritesAuthorized()` восстанавливать пока нечего (см. §2.9a); `docs/TECHNICAL_DEBT.md` RISK-41 отслеживает backup-retention/purge на будущее. Файлы: `src/lib/changesets/{contracts,schemas,services}.ts`, `src/lib/batches/{merge,contracts,services,adapters/store}.ts`, `src/lib/db.ts`, `src/lib/video-metadata/contracts.ts` (+`error-status.ts`), новый роут `src/app/api/channels/[channelId]/localizations/languages/[language]/propose-deletion/route.ts`, `src/components/languages-manager.tsx`.
- **Перенос языка на другой код (BL-232, 2026-10-29, PRD-REQ-0043, owner msgs 3782/3784).** `changesets.proposeLanguageMove({channelId, fromLanguage, toLanguage, videoIds?}, {createdBy})` — один Change Set source `deletion`: на каждое видео с `fromLanguage` пара `delete` для него и пара `add` для `toLanguage` с тем же синхронизированным текстом (байт в байт). Пропускает и перечисляет видео, где `from`/`to` — собственный язык (или базовый язык канала), и видео с пустым заголовком `from` (пустое описание переносится как `""`); при заданных `videoIds` — названные видео без `from` (`notCarryingSourceVideoIds`); если `to` уже есть — он остаётся, удаляется только `from` (оба текста в ответе и заметке к изменению). Набор помечен в `schemaVersion` (`language-move/1 from to`). Batch пишет пару одним `videos.update` через общий merge; правило `unpairedMoveHalves` (`src/lib/batches/targets.ts`) не даёт отправить одну половину переноса без другой — в send-approved и в ручном `createBatch` (`send_unpaired_language_move`); перед записью `missingMoveTargets` (`merge.ts`) делает строку CONFLICT, если у `to` нет заголовка ни в свежем чтении, ни в этой же строке. Как и любая запись Batch, видео с собственным языком, отличным от базового языка канала, в той же записи выравнивается на базовый (FO-REQ-0022); `get_change_set.languageAlignments` показывает такие видео до одобрения. Входы: кнопка ⇄ у столбца в `languages-manager.tsx` → `POST .../localizations/languages/[language]/propose-move`; MCP `agent_localization_propose_language_move` (DRAFT, агент своего канала, Agent API 4.10.0).
- **Чего нет:** реальной записи локализаций в YouTube, immutable backup/audit log для write-операций, batch executor, CLI/MCP-инструментов для change sets, restore-UI для deletion-предложений (см. выше). Per-item execution ledger частично появился в Phase 5 Slice 1 — см. 2.9a.

- **Найденные и исправленные в ходе Slice 3 баги Foundation-слоя:** несколько функций в `src/lib/db.ts` (`transitionLedgerRowStatus`, `markBatchTerminal`, `listStoredLedgerRowsByBatch`, `listStoredAttemptsByBatch`) никогда не принимали параметр `database` и продолжали писать/читать singleton вместо переданной изолированной БД — баг не проявлялся в тестах на fake-store (Slice 1/2) и обнаружился только при добавлении реального SQLite-теста восстановления после сбоя. Также обнаружено расхождение: `src/lib/db.ts` держит собственную копию типа `LedgerStatus`, не синхронизированную с `src/lib/batches/contracts.ts` (не содержала `DRY_RUN_COMPLETE`/`AWAITING_EXECUTION`) — исправлено вручную, отмечено как известный source-of-truth риск (см. `docs/TECHNICAL_DEBT.md`).

- **Статус: Slices 1-2 из утверждённого пятислойного implementation plan Phase 5** (`docs/acceptance/PHASE_5_ACCEPTANCE.md`, статус APPROVED). Slice 1: сущность `Batch` с неизменяемым составом (`AC-BATCH-01/02`), per-video execution ledger (`AC-LEDGER-01`), durable двухфазная (`INTENDED` → результат) запись attempt-намерения (`AC-ATTEMPT-02/03`), явная модель состояний и atomic-локи (`AC-CONCURRENCY-01/02/03`) — включая исправление от 2026-09-17 по итогам Foundation safety verification: слот `active_attempt_id` на ledger row (не только UNIQUE-констрейнт) гарантирует не более одного активного attempt на строку под реальной конкурентностью.
- **Slice 2 (SAFETY PREPARATION), добавлено 2026-09-17:** переиспользование `write-context.assertWriteChannel` перед любой работой batch (`AC-GUARD-01`); re-check approval/validation/conflict каждого `Change` как при создании batch, так и непосредственно перед подготовкой записи, одной и той же функцией (`AC-MERGE-04`, `AC-BATCH-03`); `src/lib/batches/merge.ts` — чистая логика defaultLanguage-проверки (`AC-DEFAULTLANG-01/02`), pre-write conflict detection против **свежего** fetch (`AC-CONFLICT-01`/`AC-LEDGER-04`, закрывает `RISK-03` для пайплайна подготовки), safe merge с сохранением нетронутых locale/snippet-полей (`AC-MERGE-01..03`, `AC-MULTI-01`); новый модуль `src/lib/backup/` — immutable backup с разделением item-level/infrastructure-wide отказа, никогда не перезаписывается (`AC-BACKUP-01..04`); dry-run проходит весь pipeline (identity → fetch → merge → backup) и не делает ни одного write-вызова, ledger row переходит в отдельный терминальный статус `DRY_RUN_COMPLETE`, никогда не `SUCCESS` (`AC-DRYRUN-01/02/03`). Явно разделены batched preliminary fetch (`fetchPreliminaryBatchContext`) и обязательный fresh single-video fetch (`fetchFreshVideoContext`) — merge/conflict/backup всегда используют только второй.
- **Файлы:** `src/lib/batches/{contracts,schemas,services,merge,ledger-state,index}.ts`, `adapters/{store.ts,write-executor.fake.ts,write-executor.youtube.ts,youtube-api.ts}`; ключевые новые тесты Slice 5: `resume-100-video.acceptance.test.ts`, `concurrency-execution.integration.test.ts`, `write-path-inventory.test.ts`; `src/lib/backup/{contracts,services,index}.ts`, `adapters/filesystem-store.ts`; новые таблицы в `src/lib/db.ts` (`batches`, `batch_ledger_rows` — с `active_attempt_id`, `batch_attempts`, `video_execution_locks`), схема инициализации остаётся аддитивной (`docs/decisions/0001-additive-idempotent-schema-strategy.md`).
- **Чего явно нет после завершающей задачи** (см. отчёты о реализации, не путать с «готово»): CLI-команд и MCP-инструментов для этого модуля по-прежнему не существует (`DEC-OQ-5`, планируется отдельной будущей фазой) — только минимальный dry-run-only Web UI/API (§2.10/§2.11). `AC-CONCURRENCY-03`'s полный сценарий закрыт частично (lock-примитив под гонкой двух батчей проверен; полный two-batch orchestration race через `executeBatch` — да, теперь тоже проверен, см. выше). Live-валидация (реальный канал, реальный OAuth) не проводилась ни для одного сценария. **Ни один код-путь в репозитории не может достичь реального вызова `videos.update`** — реальный `WriteExecutor` существует (`adapters/write-executor.youtube.ts`), но не сконструирован нигде в production-коде (проверено автоматическим инвентарным тестом, включающим и новые API-роуты, не только вручную), а его собственный `attemptWrite` безусловно отказывает через `assertLiveWritesAuthorized()` независимо от того, кто и как его вызовет.

### 2.9au Несколько наборов изменений одним пакетом, вкладка «Записаны в YouTube» (BL-198, `docs/roadmap/plans/SEND_TOGETHER_PLAN.md`, ADR 0020 Amendment 1) — **IMPLEMENTED** (влито в `dev` 2026-10-18, de4c8596)

- **Сервис:** `src/lib/batches/send-approved.ts`.
  - `planSendTogether` только читает.
  - `createBatchForChangeSets` собирает одну строку на видео со всеми отправляемыми изменениями выбранных наборов: один `videos.update`, 52 единицы.
  - Коллизии разных наборов:
    - Коллизия — одно и то же (видео, язык, поле) или удаление языка рядом с любым изменением этого языка.
    - Без `resolutions` сервис отвечает `send_merge_conflicts`.
  - BL-226: перевод, который останется без названия (по сохранённой копии видео; название из другого набора той же отправки
    засчитывается), — `send_untitled_translations` до любых отклонений и до создания пакета; план показывает их в `untitled`.
    Предел: план считает до выбора вариантов, поэтому случай «один набор удаляет язык, другой даёт только описание» он не
    покажет — его откажет сама отправка после выбора (ничего не отклонено и не создано).
    - При живой отправке невыбранные варианты отклоняются через `createChangeSetCore().rejectChange`. Пробный прогон их только не включает.
    - В аудит пишется событие `MERGE` по строкам.
  - Отправка одного набора (ADR 0020) идёт через тот же сервис без изменений.
- **«Записано»:** есть более новая успешная строка настоящего пакета, или сохранённая копия видео уже держит одобренное значение (`remoteHoldsApprovedValue`, `changesets/diff.ts`). Тем же правилом не отправляется повторно уже записанное.
- **`createBatch`** отклоняет строку с двумя изменениями одной цели (`duplicate_target_in_row`).
- **Маршруты:** `POST .../change-sets/send-together/plan` и `POST .../change-sets/send-together` (`{ changeSetIds, resolutions?, dryRun? }`). Список наборов получил поле `writtenCount`.
