### 2.9p Phase 8 follow-up, слайс 3/4: сравнение видео по сопоставимому возрасту (`getComparableAgeComparison`) — **IMPLEMENTED**, в `dev`

- **Статус:** та же ветка задания, что §2.9o («Ок, доделай эти функции»), `docs/roadmap/BACKLOG.md` BL-076. Продолжение того же списка недостающих возможностей Phase 8 из `docs/roadmap/FUTURE_PHASES.md` §4 ("comparing videos at comparable ages").
- **Что делает:** для 2-10 `videoIds` одного канала выравнивает уже собранные строки `video_metrics_daily` по числу дней с момента публикации (а не по календарной дате), так что видео с разными датами публикации можно сравнивать в одной и той же точке их собственного жизненного цикла — как «Compare videos» в реальной YouTube Studio.
- **Pacific-Time выравнивание дня 0:** `metricDate` — это Pacific-Time календарный день (собственная конвенция Analytics API), а `publishedAt` — UTC-момент из Data API v3. День 0 вычисляется как Pacific-Time календарная дата `publishedAt` (`toPacificCalendarDate`, `src/lib/analytics/comparable-age.ts`, чистый модуль без I/O), а не UTC-дата — иначе видео, опубликованное вскоре после полуночи UTC, сместилось бы на целый день относительно остальных сравниваемых видео. Полный разбор — `docs/ARCHITECTURE.md` §14.10.
- **Только аддитивные метрики:** явный allowlist `CUMULATIVE_COMPARISON_METRIC_NAMES`, исключающий every ratio/average-метрику из `ANALYTICS_METRIC_NAMES` (`averageViewDuration` и т.п.) — суммировать долю/среднее по дням бессмысленно.
- **Пропущенный день — это "неизвестно", а не выдуманный ноль.** Сознательно НЕ переиспользует `analytics_collection_runs` для вывода "известного нуля" на уровне отдельного видео (та же нерешённая проблема "было ли это видео реально запрошено в конкретном прошлом запуске", что уже описана в §2.9o/`docs/ARCHITECTURE.md` §14.9/§14.10) — реальная строка `video_metrics_daily` это единственный факт "известно"; кумулятивная сумма останавливается на последнем непрерывном известном дне от дня 0, никогда не перескакивает пробел.
- **Реальное ограничение покрытия данных (подтверждено прямым запросом к БД двух реальных каналов перед проектированием):** суточный автосбор покрывает только последние ~7 календарных дней за запуск, а не «первые 7 дней жизни видео» — видео старше ~1-2 недель до начала регулярного сбора обычно не имеет данных за дни 0-7. Механизм бэкфилла сознательно НЕ добавлен (расширение окна автосбора или бэкфилл — вне рамок этого слайса, ежесуточный gate свежести — явное правило владельца).
- **Никаких рейтингов/"outperforming"-формулировок/итогового вердикта** — только сырые факты (`docs/roadmap/FUTURE_PHASES.md` §4).
- **Файлы:** `src/lib/analytics/comparable-age.ts` (пурая арифметика + allowlist, свои тесты), `getComparableAgeComparison` (`services.ts`), `GET .../analytics/comparable-age`, MCP-инструмент `analytics_comparable_age`, CLI `analytics comparable-age` — все read-only, не гейтятся, тот же паттерн что `analytics_data_quality`.

Пропущенные недели никогда не досчитываются задним числом (та же философия "no backfill", что уже в §2.9p).
- **`status: "final"` vs `"provisional"` (совет советника, 2026-09-23):** триггер по локальному времени оператора не совпадает ни с лагом отчётности Analytics API (1-2 дня), ни с Pacific-Time нумерацией дней `video_metrics_daily` — для оператора вне Pacific Time последний день только что завершившейся недели может быть ещё не собран в момент срабатывания. Отчёт помечается `"provisional"`, если хоть одна дата ЕГО СОБСТВЕННОЙ недели ещё не покрыта/слишком свежая (`computeDataQualityReport` за эту неделю); следующая загрузка дашборда перегенерирует (заменяет) provisional-отчёт за ту же неделю, как только данные дособерутся, но `"final"`-отчёт больше никогда не трогается.
- **`percentChange` — `null` целиком, если ЛЮБАЯ из двух недель не покрыта полностью** — иначе сравнение измеряло бы полноту сбора данных, а не реальное изменение (`FUTURE_PHASES.md` §4 "avoid unsupported conclusions from small samples") — именно та ситуация, в которой сейчас реально находится канал "Tropico Jazz" (§2.9o).
- **`syncedVideoTotals`, а не «тотал по каналу»:** явно поименовано и задокументировано (`SYNCED_VIDEO_TOTALS_METRIC_DEFINITIONS`, встроено в каждый сохранённый отчёт) как сумма по уже синхронизированным видео — то же самое ограничение недосчёта, что уже задокументировано в `docs/ARCHITECTURE.md` §14.8.
- **Provenance:** каждый сохранённый отчёт несёт `reportFormatVersion`, `generatedAt`, `source`, `metricDefinitions`, и при каждом ЧТЕНИИ (не только записи) заново проверяется строгой zod-схемой — повреждённая строка в БД падает громко (`validation_failed`), а не отдаёт частичный отчёт.
- **Схема:** `analytics_weekly_reports` (SCHEMA_MIGRATIONS версия 14), один ряд на `(channel_id, week_start_date)` (UNIQUE-индекс), `report_json` хранит весь сериализованный отчёт. Сознательно не в `SNAPSHOT_TRANSFERRED_TABLES` (производные, пересчитываемые данные).
- **Триггер-роут:** `POST .../analytics/weekly-reports/generate-if-due`, вызывается раз на монтирование дашборда, ПОСЛЕ уже существующего auto-collect-триггера (через `.finally()`), гейтится `src/proxy.ts` как любая мутирующая POST.

### 2.9z Impressions и CTR через YouTube Reporting API (BL-114, `docs/decisions/0014-youtube-reporting-api-gateway-child.md`) — **реализовано, слито в `dev` (`b1456c9`); статус и квота — на ветке `feature/bl-114-reach-status-and-quota`**

- **Зачем:** показы миниатюр и CTR недоступны на `reports:query` Analytics API (live-проверка, `src/lib/analytics/contracts.ts`); они есть только в Reach-отчётах Reporting API v1 — ежедневные файлы по подписке (job).
- **Шлюз:** `src/lib/youtube-read-gateway/reporting-api.ts` (третий `googleapis`-потомок) — `reportTypes.list`, `jobs.list`, идемпотентный `ensureReportingJob`, `jobs.reports.list`, скачивание файла (токен уходит только на `https://youtubereporting.googleapis.com`), разбор CSV по имени колонки. Свой тумблер **Reporting reads** (по умолчанию включён) и счётчик `reporting_reads`. **Создание job — не запись YouTube** (решение владельца, ADR 0014): без Live writes и без write-gateway.
- **Модуль:** `src/lib/reach-reports/` (независим от `analytics`, §M): `syncReachReports` (job → новые файлы → импорт, сбой одного файла не останавливает остальные; `onlyIfDue` — не чаще раза в 6 ч) и `getChannelReach` (локальное чтение, `state`: `no_job` / `waiting_for_first_report` / `ready`; отсутствие данных ≠ ноль; CTR агрегируется взвешенно по показам). Файл целиком отклоняется при чужом `channel_id`, нечитаемой дате/числе или дубле (видео, день). Файл за уже импортированный период с более поздним `createTime` заменяет строки старого (транзакция).
- **Схема:** v38 — `reporting_jobs`, `reporting_report_files`, `channel_reach_daily` (device-local, как `video_metrics_daily`; authorized по III.E.4.b); v40 — `reporting_sync_attempts` (последняя попытка синка на канал: время, исход `ok`/`partial`/`failed`, текст ошибки, упавшие файлы).
- **Статус запросов (2026-10-03, владелец: статус живёт во вкладке Analytics, в Settings — только квота):** `getReachStatus` + `GET /api/channels/[id]/reach/status` (локально, без вызова Google; добавляет `readsEnabled`) → блок «Report subscription status» в `reach-panel.tsx` (`reach-status-block.tsx`): job id и время создания, ожидаемое время первого файла (+48 ч) с пометкой «просрочено», последняя попытка и её ошибка, упавшие файлы, следующая автопроверка, список файлов. Сбой до импорта (нет scope, API выключен, тумблер off) теперь записывается и не теряется; неудачная (`failed`) попытка автозапуск НЕ троттлит — причина обычно исправима, и следующий вход в дашборд должен повторить (троттлят `ok`/`partial`).

- **Точки входа:** `POST /api/channels/[id]/reach/sync`, `GET /api/channels/[id]/reach`; карточка в Analytics → Content (`reach-panel.tsx`); автозапуск при входе в дашборд (независимо от автосбора Analytics) — с BL-141 (2026-10-06) для **всех** подключённых каналов: `POST /api/reach/sync-all` → `syncAllReachReports`, каждый канал со своим токеном (`channels.connected_user_id`) через тот же `syncReachReports` и его `assertActiveChannel` (если владелец токена переключился на другой канал — отказ, без синка); активный канал — с токеном сессии; сбой одного канала не мешает остальным; у фоновых каналов неудачная попытка тоже откладывает следующую на 6 ч, причина «не проверен» пишется в их `reporting_sync_attempts`; ответ показывает только активный канал сессии (ADR 0004); риск — RISK-112; MCP `agent_query_channel_reach` (только чтение).
- **Чего нет:** Reach combined (разбивка по источникам/устройствам); MCP-инструмента, запускающего синхронизацию (её делает приложение); названий видео в таблице (только `videoId`). **Не подтверждено на реальных данных:** формат даты и масштаб CTR (доля или проценты) — первые файлы ожидаются ~2026-10-03.
