- **Тумблер "Data API reads" (2026-09-22, Settings tab):** `createYoutubeClient` вызывает `assertDataApiReadsAuthorized()` (проверяет `getDataApiReadsEnabled`, по умолчанию `true`, не сбрасывается при рестарте) перед созданием клиента — единственная точка входа для ЛЮБОГО read- или write-вызова Data API v3 (включая построение write-клиента Batches и identity-проверку `write-context` перед записью — намеренная связь, не баг: без чтения write-путь всё равно не может безопасно продолжить). Живьём проверено в браузере: выключение тумблера корректно ломает Content-таб с понятной ошибкой, включение обратно — восстанавливает.
- **Классификация ошибки превышения квоты (добавлено 2026-09-22, owner instruction, Telegram: «Сделай правильную обработку этого события... чтобы агенту это тоже было транслировано корректно»):** новый `error-classification.ts` — `classifyYoutubeReadError` (проверка `403 quotaExceeded`/`dailyLimitExceeded` → `DomainError` с кодом `youtube_quota_exceeded`, 429; любая другая ошибка пробрасывается БЕЗ ИЗМЕНЕНИЙ). **Применяется один раз в самом конструкторе клиента** (`createYoutubeClient`/`createYoutubeAnalyticsClient`), а не в каждой из ~15 точек вызова по отдельности — по прямому уточнению владельца («у нас же один шлюз который взаимодействует с API, он и может и обрабатывать / переводить это сообщение»). `wrapYoutubeClientForQuotaClassification` строит НОВЫЙ объект (через `Object.defineProperty`), а не `new Proxy(client, {...})` напрямую — живой проверкой найдено, что реальный клиент `googleapis` определяет свойства ресурсов (`.channels`, `.videos` и т.д.) как non-configurable/non-writable, что нарушает инвариант `Proxy`'s `get`-ловушки и роняет реальный Content sync ошибкой `TypeError`; тест на это добавлен (фикстура с `Object.defineProperty`, воспроизводящая именно эту форму). Намеренно НЕ вычисляет момент сброса квоты (только текст «сбрасывается в полночь по Тихоокеанскому времени») — граница сброса для Analytics API отдельно не проверена, неверный machine-readable timestamp хуже отсутствующего. Отдельный от `classifyYoutubeWriteError` (write-путь, AC-QUOTA-02, `FAILED/permanent/systemic`, останавливает весь batch). Проверено: MCP (`toolErrorResult`) и CLI уже передают `{code, message, details}` для любого `DomainError` без дополнительных изменений.
- **Зависимости:** `src/lib/auth.ts` (создание OAuth2-клиента).
- **Read/Write:** содержит и read-, и write-методы (`applyVideoMetadataUpdate`, playlist create/update/delete/insert/delete-item). Методы, используемые `channel-sync`, — только read (`channels.list`, `playlistItems.list`, `videos.list`).
- **Важные ограничения безопасности:** не должен дублироваться — новый код обязан расширять этот файл, а не создавать параллельный клиент (`docs/PROJECT_SPEC.md` §3).

### 2.9f Live-writes / Gate B toggle + MCP connection toggle (Settings tab) — **IMPLEMENTED**, does NOT close Gate B

- **Ответственность:** owner-controlled, persisted app-wide flags: «Live writes» (Gate B, owner instruction 2026-09-21, BL-045) и «MCP connection» (owner instruction 2026-09-21, BL-047 — переименован и инвертирован из прежнего «MCP restricted mode»: *«По началу MCP / агент от всего отключен и получит доступ только если я зайду в настройки и переключу этот тумблер»*).
- **Файлы:** `src/lib/db.ts` (`appSettings` таблица, SCHEMA_MIGRATIONS версия 7, `getLiveWritesEnabled`/`setLiveWritesEnabled`/`getMcpRestrictedModeEnabled`/`setMcpRestrictedModeEnabled`), `GET/POST /api/settings`, `src/components/live-writes-settings.tsx` (Settings tab), `src/lib/batches/adapters/write-executor.ts` (Layer 1), `src/lib/batches/adapters/write-executor.youtube.ts`'s `assertLiveWritesAuthorized` (Layer 2, теперь `async`, перечитывает настройку при каждом вызове вместо безусловного throw), новый роут `POST .../batches/[batchId]/execute`.
- **Двухслойный барьер сохранён, не заменён одним чтением:** слой 1 — `createLiveWriteExecutorIfEnabled` конструирует реальный `WriteExecutor` только если настройка включена (иначе `null`, роут отказывает до вызова `executeBatch`); слой 2 — сам executor независимо перечитывает ту же настройку прямо перед сетевым вызовом. Оба слоя проверены тестами (`write-executor.youtube.test.ts` — есть и off-, и on-case; `write-path-inventory.test.ts` обновлён с явным, единственным разрешённым исключением на новый роут, а не ослаблен целиком).
- **ADR 0044 (2026-10-19, владелец, msg 3157): «Запись в YouTube» включена по умолчанию и сама не выключается.** Ни старт, ни остановка сервера, ни 10 минут простоя её не сбрасывают; выключает только владелец, и выключение сохраняется. Lease веб-сервера остался как проверка «приложение работает»: истёкший lease отказывает в записи, но больше не сохраняет «выкл». Пункт ниже описывает прежнюю модель (история).
- **«Выключено по умолчанию каждую сессию»:** Live writes действует только пока жива сессия веб-сервера. `getLiveWritesEnabled` возвращает true, только если тумблер включён и lease сессии свежий (TTL 3 мин). Веб-сервер продлевает lease каждые 30 с и сбрасывает тумблер при старте и при штатной остановке (`src/instrumentation.ts`). При аварийной остановке на любой ОС, включая `taskkill /F` на Windows, тумблер гаснет через TTL. MCP и CLI флаг не сбрасывают и lease не продлевают (аудит 2026-10-01, H1 и ревью).
- **MCP connection (BL-047, 2026-09-21):** по умолчанию выключен — в этом состоянии `createMcpServer` не регистрирует НИ ОДНОГО инструмента вообще, включая read-only (`whoami`, `list`, `changeset_list`, `channel_sync` и т.д.), не только write/identity-инструменты, как было раньше у «restricted mode». Единая точка проверки — один булев параметр `connectionEnabled`, читаемый внутри `registerTool` для каждого инструмента, вместо прежнего списка-исключения на 8 конкретных write-инструментов. В отличие от Live writes, **сохраняется между перезапусками** — не сбрасывается на каждый boot (явное решение владельца проекта, разовая настройка). Env-переменная `MCP_RESTRICTED_MODE` удалена полностью — единственный способ включить это теперь тумблер в Settings. Эндпоинт `/api/mcp` читает настройку на каждый запрос (stateless, свой `createMcpServer` на запрос — ADR 0013), поэтому изменение действует со следующего вызова агента, без перезапуска клиента.
- **UI:** `ConfirmDialog` перед включением Live writes (пояснение, что это слой 1 барьера, не сама запись); в Batches — чекбокс «Create as a real, live batch» при создании (виден только если тумблер включён) и кнопка «Execute (real write)» на уже созданном live-batch, тоже за `ConfirmDialog` с явным текстом (канал, число видео, число полей, напоминание что это реальная запись).
- **Не закрывает Gate B:** ничего из требуемой в acceptance-контракте живой валидации (реальный тестовый канал, реальный OAuth, сценарии AC-MERGE-01/05/GUARD-01/CONFLICT-01/RESUME-01/E2E-01) этим не выполнено — существование тумблера не является доказательством, что она проводилась. `docs/TECHNICAL_DEBT.md` RISK-09 остаётся `OPEN`, с явной пометкой «owner-gated, not unconditional» вместо «unconditional».
- **Live-проверено в браузере** на канале Tropico Jazz: включение тумблера показывает `ConfirmDialog`, после Save/Apply в Batches появляется чекбокс live-batch; создание batch с ним снятым (обычный dry-run путь) не регрессировало; кнопка Execute корректно не показывается для dry-run batch. Реальная отправка (клик Execute) сознательно НЕ протестирована в рамках этой задачи — это отдельное решение о канале/видео для теста, ещё не принятое владельцем.
- **605 → 607 тестов** (`write-executor.youtube.test.ts`); `npx tsc --noEmit`, `npm run lint`, `npm run build` чисты.

### 2.9at Экраны не тратят квоту на уже сохранённые данные (BL-197) — **IMPLEMENTED** (влито в `dev` 2026-10-18, bcdf8e8a)

- **Шапка:** `GET /api/youtube/channel-info` читает `channels.list mine` один раз на вход. Дальше 6 ч отвечает из памяти процесса (`src/lib/channel-access/live-channel-memo.ts`, ключ — пользователь сессии). Память сбрасывается при входе через Google (`auth.ts` `signIn`), при отключении канала и при перезапуске. Каждый ответ по-прежнему вызывает `activateChannel` (ADR 0004). Живое чтение подписано в журнале квоты как `channel_header`. Проверку входа делает `/api/channel-connections/health`, она без квоты.
- **Переключатель каналов:** `use-connected-channels` шлёт `POST /api/channels/sync { onlyIfStale: true }`. Ответ `{ skipped: true }` без YouTube, если у канала, прочитанного живьём для этого входа (память шапки), есть копия этого же входа не старше 6 ч; без живого чтения (новый вход, перезапуск) синхронизация идёт (`channel-sync/freshness.ts`, общее правило с `publishing/refresh-stale`). Новый канал без своей копии синхронизируется сразу. Явный `channelId` и синхронизация без флага выполняются всегда.
- **Главная:** сводка канала без `refresh=1` — то же правило `preferLocal`, что у вкладки Аналитики.
- **Источники трафика и устройства канала:** `getChannelBreakdown` сначала пробует `answerChannelBreakdownFromStore` (`analytics/breakdowns.ts`): сумма сохранённых дней `analytics_breakdown_daily`, если они покрывают период (правило `isRangeFullyCovered`, как у сводки: последние 2 дня засчитываются с тем, что сохранено, поэтому сумма может быть меньше живой на ещё не собранные дни). Любая ошибка пути из базы — живой запрос. MCP `agent_query_channel_breakdown` идёт тем же путём. Остальные четыре разреза Аудитории не хранятся и остаются живыми.
- **Плейлисты для выбора:** `GET /api/youtube/playlists` → `listPlaylistsRemembered` (`playlist-management/playlist-list-memo.ts`, 1 ч на вход). Любое изменение плейлистов через ядро, вход через Google и отключение канала сбрасывают память; общий помощник `src/lib/user-ttl-memo/` (у шапки тоже) не даёт чтению, начатому до сброса, вернуть старый ответ. `?refresh=1` — кнопка «Обновить список». `listPlaylists` для MCP и CLI остаётся живым.
- **Охват:** после неудачной автоматической попытки активный канал ждёт `FAILED_ACTIVE_RETRY_AFTER_MINUTES` (60 мин), фоновый — 6 ч. `nextAutoCheckAt` в статусе учитывает эту паузу.
- **Не входит:** окно видео (`videos.list` перед правкой) и четыре нехранимых разреза Аудитории. Схема не менялась.
