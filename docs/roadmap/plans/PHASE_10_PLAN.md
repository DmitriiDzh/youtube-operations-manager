# Phase 10 Plan — Decision & Experiment Engine

Produced 2026-09-20 per `docs/roadmap/FUTURE_PHASES.md` §9's planning sequence, covering backlog
item `BL-005` (`docs/roadmap/BACKLOG.md`). **This is a plan, not an implementation.** Phase 10
depends on Phase 8 (facts) and Phase 9 (candidates) actually existing to have anything real to
reason about — this plan is written with that dependency explicit, not glossed over.

## 1. Current repository state relevant to this phase

- The closest existing analog is the `changesets`/`batches` pipeline (Phase 4/5): propose → draft
  state → human approval → controlled execution → audit trail. Phase 10 needs the same *shape*
  of pipeline (propose → approve → execute → observe outcome) but for a fundamentally different
  kind of object — an experiment/hypothesis about channel strategy, not a metadata edit. Reusing
  the shape (not the entities) is the right level of imitation; a `Change`/`ChangeSet` row is
  "change this video's title to X," which has nothing in common with "hypothesis: shorter titles
  increase CTR for this channel" beyond the review-before-consequential-action pattern.
- Nothing resembling a hypothesis, experiment, or decision entity exists in `src/` today. This
  phase is fully greenfield, and — per this plan's own §1 above for Phases 8/9 — depends on those
  phases' data existing (metrics from Phase 8, candidates from Phase 9) to generate any real
  hypothesis from; without them, this phase can only design the container, not populate it with
  anything meaningful yet.
- `docs/audit/` and `src/lib/audit/` (Phase 5) already establish a durable, append-only audit-log
  pattern for consequential actions — the "recording lessons learned" and "reusable decision
  history" goals in `FUTURE_PHASES.md` §6 should reuse this pattern's shape (append-only,
  timestamped, linked to what triggered it) rather than inventing a second audit mechanism
  (`AGENTS.md` §D).

## 2. Existing capabilities vs. missing dependencies

| Capability Phase 10 needs | Status |
|---|---|
| A propose → approve → execute pipeline shape to imitate | **Exists** (`changesets`/`batches`), shape only — entities must differ |
| An append-only audit-log pattern to imitate | **Exists** (`src/lib/audit/`) |
| Real historical metrics to generate hypotheses from | **Missing** — depends on Phase 8 (`docs/roadmap/plans/PHASE_8_PLAN.md`) actually being implemented, not just planned |
| Real market/candidate data to generate "new channel concept" hypotheses from | **Missing** — depends on Phase 9 similarly |

| "Already-authorized product interfaces" for controlled execution | **Partially exists** — depends on which kind of action an approved experiment executes; if it's a localization change, the existing Change Set/Batch pipeline already is that interface; if it's something else (e.g. a new channel), no interface exists yet |

## 3. Smallest useful vertical slice

**A hypothesis/decision *record-keeping* model with manual entry, no automatic hypothesis
generation and no automatic execution.** Concretely: `hypotheses` (statement, supporting
evidence references — pointing at Phase 8 metrics rows and/or Phase 9 evidence rows once those
exist, or manually-entered text if not), `experiments` (linked hypothesis, success/stopping
criteria, budget estimate, status), and `decisions` (linked experiment, what was approved, by
whom, when, outcome once observed) — all populated by a human typing into a form at first, not
generated by an AI proposing them. This proves the record-keeping shape and the
evidence/hypothesis/decision/outcome separation `FUTURE_PHASES.md` §6 requires, before any
automatic generation or execution logic is attempted.

## 4. Scope and explicit non-goals for this phase, once assigned

**In scope (eventually, on separate assignment):**
- `hypotheses`/`experiments`/`decisions` tables, additive, explicitly separate from
  `change_sets`/`changes` (an experiment is not a metadata edit, even when its eventual executed
  action happens to be one).
- Manual-entry Web UI/API for all three, plus manually recording an observed outcome against a
  `decisions` row.
- A durable decision-history view (list/filter past decisions and their outcomes), reusing the
  existing audit-log's append-only pattern.

**Explicitly out of scope, regardless of how this phase eventually proceeds:**
- Any AI-generated hypothesis or recommendation — that's a later slice, and per
  `FUTURE_PHASES.md` §6's own constraint, "no consequential action executes merely because an AI
  agent proposed it," so even once AI generation exists, it produces a `hypotheses` row awaiting
  human approval, never anything self-executing.
- Automatic/controlled execution of an approved experiment — this needs its own design per
  action type (a localization experiment executes through the existing Batch pipeline; a "new
  channel concept" experiment might not have any existing execution interface at all yet) and its
  own safety review before any code reaches a real side effect.
- Treating Phase 8/9 as complete dependencies — this plan explicitly does not assume their
  eventual implementation exists; the record-keeping slice above works even with zero real
  metrics or candidates, at the cost of every hypothesis being manually justified rather than
  evidence-linked.

## 5. Interfaces, data structures, and security boundaries needed

- Additive tables, e.g.:
  ```sql
  CREATE TABLE IF NOT EXISTS hypotheses (
    id TEXT PRIMARY KEY,
    channel_id TEXT REFERENCES channels(id),   -- nullable: a "new channel concept" hypothesis has no existing channel yet
    statement TEXT NOT NULL,
    evidence_refs_json TEXT NOT NULL,          -- pointers into video_metrics_daily / research_evidence rows, or free text if none exist yet
    created_at INTEGER NOT NULL DEFAULT (unixepoch())
  );
  CREATE TABLE IF NOT EXISTS experiments (
    id TEXT PRIMARY KEY,
    hypothesis_id TEXT NOT NULL REFERENCES hypotheses(id),
    success_criteria TEXT NOT NULL,
    stopping_criteria TEXT NOT NULL,
    budget_estimate TEXT,
    status TEXT NOT NULL                       -- proposed | approved | running | concluded | abandoned
  );
  CREATE TABLE IF NOT EXISTS decisions (
    id TEXT PRIMARY KEY,
    experiment_id TEXT NOT NULL REFERENCES experiments(id),
    approved_by TEXT NOT NULL,
    approved_at INTEGER NOT NULL,
    outcome TEXT,                               -- null until observed
    outcome_recorded_at INTEGER
  );
  ```
- Channel-context validation applies wherever `channel_id` is non-null, exactly as `AGENTS.md`
  §F requires for any channel-scoped resource.
- Security boundary: `decisions.approved_by` must be a real identity, never a default/system
  value, and no code path should be able to set `outcome`/`approved_at` except through an
  explicit human action — this is the human-approval gate `FUTURE_PHASES.md` §6 requires,
  enforced structurally (no default value, no auto-population), not just by convention.

## 6. Proposed implementation slices (for whichever future assignment picks this up)

1. `hypotheses`/`experiments`/`decisions` tables (additive migration) + tests.
2. Manual-entry API routes + minimal Web UI for creating/viewing each.
3. Manual outcome-recording action against a `decisions` row.
4. (Separate, later assignment, likely long after Phase 8/9 are real) evidence auto-linking from
   real Phase 8/9 data, AI-assisted hypothesis drafting (draft-only, per the existing AI
   Localization pattern), and any automatic execution wiring.

## 7. Acceptance criteria (drafted from the requirement, per `AGENTS.md` §L)

For slices 1-3 above, once assigned:
- A test proves `decisions.outcome`/`outcome_recorded_at` cannot be set at `decisions` row
  creation time — only through the separate outcome-recording action, verifying the
  approval/outcome separation is structural.
- A test proves a `hypotheses` row with `channel_id` set to a channel the current session isn't
  authorized for is rejected (channel-context validation, `AGENTS.md` §F).
- A negative test: creating an `experiments` row without both `success_criteria` and
  `stopping_criteria` is rejected — `FUTURE_PHASES.md` §6 requires experiments to have these
  defined, not optionally.

## 8. Required project-owner decisions before implementation can start

- Confirm the manual-entry-only first slice is the right starting point given Phase 8/9 don't

  finalized.
