# 0023. Remote media generation: human-approved pod sessions, S3-only transport, per-device key file

Status: Accepted

**Date:** 2026-10-05. **Assigned by** the owner (Telegram, msgs 1471–1484): research, plan and
"Да, приступай к реализации". Research: `docs/roadmap/plans/MEDIA_GENERATION_RUNPOD_COMFYUI_SYNCTHING_RESEARCH.md`;
plan and acceptance criteria: `docs/roadmap/plans/PHASE_14_PLAN.md`.

## Context

The channel agent must be able to generate images, video and music on RunPod/ComfyUI through this product,
with models kept on the server only as long as needed and every result pulled to the machine running the
app. RunPod bills a *stopped* pod's disk at twice the running rate, a network volume at $0.07/GB/month, and
offers an S3-compatible API to that volume that works while no pod exists. ComfyUI has no authentication
and RunPod's HTTP proxy is public. Credentials must be entered in Settings and stored encrypted per device
(owner, msg 1480).

## Problem

How a session is authorised and paid for, how files travel, how the pod is secured, and where the secrets live.

## Alternatives

- **Syncthing on the pod** (the owner's first idea): push-based, but it needs a daemon and a TCP port per
  pod, an identity on the volume, and it cannot run while the pod is gone. Rejected once the owner accepted
  S3 (msgs 1476–1478): `/history` names the exact files, so pull is enough.
- **Serverless `worker-comfyui`**: cheaper for rare jobs, but each job pays a cold start, and an iterative
  session is what the agent does. Rejected for now; the S3 transport keeps it possible later.
- **Approval per job** (ADR 0021's shape): would block every iteration. Rejected (D3).
- **Env-var encryption key** (ADR 0008's shape): the owner asked for no `.env` step. Rejected (msg 1480).
- **Stop the pod when idle**: doubles the disk bill. Rejected: the only idle state is *terminated*.

## Decision

1. **Session = one pod, approved by a human (D2/D3).** The agent (or the operator) requests a session with
   `maxMinutes`/`maxUsd`; the estimate is `savedGpuPrice × minutes / 60`, computed locally. Approval is
   Web-only (`POST /api/media-generation/sessions/{id}/approve`, fenced from MCP/CLI by inventory test);
   preconditions run before any transition; the pod is created from a template with the network volume at
   `/workspace`, `8189/http` and a per-session `COMFY_TOKEN`; the route blocks until ComfyUI answers behind a
   Caddy bearer proxy (D6). A watcher terminates on idle / minutes / USD; boot sweep and shutdown hook make
   sure no pod outlives the process. `UNIQUE(open_slot)` = one open session per device.
2. **S3-only transport (D1).** Outputs are written by ComfyUI under `/workspace/exchange/<jobId>/`, pulled over
   RunPod's S3 API (hand-written SigV4, verified against the AWS test vectors), hashed twice, recorded in
   `media_exchange_files`, deleted from the volume, and registered in `creative_assets` with provenance.
   Models reach the volume through a CPU pod (`hf download`), never through a GPU pod.
3. **Outputs land in `<workspace>/99 Data Exchange/From YTM/media/<jobId>/` (D4)**, resolved by the new shared
   `src/lib/workspace-exchange/` module (extracted from research-export, AGENTS.md §M).
4. **Per-device key file.** `media_credentials` and each session's proxy token are AES-256-GCM-encrypted
   under `app-data/media-generation.key` (0600), generated by the app on first save; never an env var; a
   copied database reads as "not configured".
5. **Single gateway.** `src/lib/media-gateway/` (RunPod REST v2, S3, ComfyUI) is the only module that may
   reach a runpod.io host (inventory test); one "Media gateway" toggle and three traffic counters.
6. **Agent surface (Agent API 3.4.0 on `dev`, domain `media_generation`)**: list templates, request/get session, get
   limits, create/get/cancel job. Templates are operator-imported (D7); prompts are job parameters.

## Consequences

- RunPod REST v1 is not used (it retires 2026-11-15). The v2 list-wrapper keys are read from docs and
  confirmed by the live spike (RISK-106).
- The key file has no rotation/backup procedure (RISK-106); the two older env-key modules are unchanged.
- Jobs poll in-process; a server restart fails the in-flight job as interrupted (its pod is swept too).
- Serverless, YouTube upload of generated media and prompt libraries stay out of scope (concurrent sessions: see the amendment below).

## Amendment 1 (2026-10-05, slice 6 -- owner, Telegram msgs 1549/1551/1553)

Supersedes "one open session per device" (decision 1, AC-P14-05) and the blocking approve route:

- **Concurrent sessions.** Any number of requests may be pending; at most `maxConcurrentSessions` (setting, 1–4,
  default 3) hold a pod (`approved|starting|running|stopping`), each its own pod on the shared volume. Schema v58
  makes `media_sessions_open_slot_idx` a plain index; the bound is the approve's single guarded UPDATE (AC-P14-22).
  The daily cap at approve counts spend today plus what the other active sessions may still spend up to their
  estimates; the watcher stops every session once the day's total reaches the cap.
- **Shared/exclusive volume.** Sessions hold the volume SHARED by being active rows; a model pull or operator pod
  holds it EXCLUSIVELY with the `media_volume_lock` row. Each write is guarded by the other's absence in the same
  statement, so AC-P14-18 stays a database constraint (AC-P14-23).
- **Non-blocking approve.** The approve request validates and writes `approved`, answers at once, and the pod start
  continues in the background; every outcome is on the row (AC-P14-24). Sessions are shown in a table with live
  statuses in the new Production section; Settings keeps only the RunPod connection (AC-P14-26).
- **Balance.** Read from RunPod's legacy GraphQL API (`myself.clientBalance`) -- REST v2 has none -- through the same
  gateway and key, degrading to the v2 billing spend when that read fails (AC-P14-25).
- **Agent API 3.4.0 (MINOR):** `agent_get_media_limits` adds `openSessions` (this channel's), `maxConcurrentSessions`
  and `activeSessionCount`; `openSession` stays; a request no longer conflicts with another open session.

## Amendment 2 (2026-10-06, BL-135 -- owner, Telegram msgs 1644–1649)

Supersedes "the agent can neither approve, start nor stop a session" for ONE direction: ending. The owner asked that a finished task
not keep a pod billing until the idle timeout.

- **Release by the requesting channel.** `releaseSession` (MCP `agent_release_media_session`, Agent API 3.6.0, `bound`, behind the device
  mutation gate): only the session's own channel; `pending` → withdrawn (`rejected`), `starting`/`running` → the same stop as the owner's,
  `stopping` → returned as is, `approved` (pod still being created) and terminal → `media_session_invalid_state`. Approving, starting and
  rejecting stay Web-only; the inventory test keeps fencing `stopSession`, `approveSession`, `rejectSession` and the watcher.
- **Release when done.** A request may carry `releaseWhenDone` (schema v63 `media_sessions.release_when_done`). A request that omits it
  takes the owner's Production → Setup setting (owner 2026-10-06 msgs 1807/1810 for the owner's requests; since 2026-10-07, DEV-MSG-0001 /
  FO-MSG-0007, for agents' and the factory's requests too, on by default); an explicit value wins. Such a stop is recorded with
  `stopReason` "released after last job …". The watcher stops such a running session once it has at least one job, none is open, and a minute has passed since
  both the last job finished and the last activity. Never before the first job, never while a job runs.
