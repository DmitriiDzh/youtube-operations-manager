# Authorized YouTube writers and exceptions

This is the authoritative list referenced by `AGENTS.md` §F. It is binding exactly as if it were written in
`AGENTS.md` itself: the Change Set / localization mechanism has authority over `title` and `description` per
language only (`AGENTS.md` §F); the writers and exceptions authorized beyond that are listed here. Any new
writer or exception must be added to this file. The entries below were moved verbatim, unchanged, from
`AGENTS.md` §F on 2026-11-17 to keep that always-loaded file small; their order and wording are the original.

**One authorized exception (2026-10-02, owner, Telegram):** Batches may write the channel baseline as `snippet.defaultLanguage` for a video that has none, in the same `videos.update` as its localizations (`docs/PROJECT_SPEC.md` §14) — nothing more.

  **Extension (2026-10-04, owner, Telegram):** Batches also send the channel baseline `snippet.defaultAudioLanguage` (when one is set) on every write, because `videos.update` resets a snippet field that is left out — `docs/PROJECT_SPEC.md` §14.

  **Extension (2026-10-12, owner, Telegram msg 2665, FO-REQ-0022):** Batches also align a video whose `snippet.defaultLanguage` differs from the channel baseline to that baseline in the same `videos.update` (the title/description stay byte-for-byte; the translation goes into `localizations`) — `docs/PROJECT_SPEC.md` §14.

  **Separate authorized exception (2026-10-02, owner):** `src/lib/video-details/` (not the Change Set mechanism) may write `snippet.defaultAudioLanguage` — experimental, read-back verified; batches send only the channel baseline value (extension above), never a per-video value.

  **Second localization writer (2026-10-21, owner, Telegram msg 3257, BL-207, ADR 0045):** `src/lib/live-localizations/` may write per-language `title`/`description` (`localizations`) besides the Change Set mechanism (since BL-225 its writer is the shared `src/lib/shared-video-localizations/`, whose only callers are this module and the upload localizations below) — only to a live broadcast's video, only the stream's stored set (`live_streams.localizations_json`), through the shared merge (`src/lib/shared-localization-merge/`: other languages kept, nothing deleted, the snippet text untouched, never the video's own language) with identity check, backup, Live writes, read-back and audit — `docs/PROJECT_SPEC.md` §21.

  **Third localization writer (2026-10-22, owner, Telegram msgs 3343/3347, BL-210, ADR 0047):** `src/lib/channel-localizations/` may write a channel's OWN per-language `title`/`description` (`channels.localizations`) -- only the channel's stored set (`channel_localizations`, saved by the owner or the Factory Operator), only through the owner's «Применить» in the Web UI (no MCP or agent path reaches it), through the shared merge (other languages kept, nothing deleted, the channel's own language never written) with identity check, backup, Live writes before each write, read-back and audit. It writes nothing else of the channel: a channel without `brandingSettings.channel.defaultLanguage` is refused (the owner sets it in YouTube Studio, msg 3350) (`docs/PROJECT_SPEC.md` §21).

  **Channel branding writer (2026-10-25, owner, Telegram msgs 3482/3488, BL-223, ADR 0050):** `src/lib/channel-branding/` may write a channel's `brandingSettings.channel.description`, `brandingSettings.channel.keywords` and banner (`channelBanners.insert`, then `brandingSettings.image.bannerExternalUrl`) -- lifting msg 3350 for these fields only. Only the channel's stored draft (`channel_branding`, saved by the owner, the Factory Operator or the channel's own worker), only through the owner's «Применить» in the Web UI (no MCP or agent path reaches it), as a full read-merge-write of `brandingSettings` (every other settable field and the title sent back exactly as read), with identity check, backup, Live writes before each write, read-back and audit. Never the name, avatar, country, default language, trailer or tracking id (`docs/PROJECT_SPEC.md` §21).

  **Upload localizations (2026-10-25, owner, Telegram msgs 3511/3534/3537, BL-225, ADR 0051):** `src/lib/publishing/` may write per-language `title`/`description` (`localizations`) of a video only on the upload it makes itself of a `yt-release-package/2` -- only the package's own set (checked by the shared rules when the upload is queued), as the first step after processing (before the thumbnail), through the shared video translations writer `src/lib/shared-video-localizations/` (the shared merge: nothing deleted, the snippet text untouched, never the video's own language), with identity check, backup, Live writes immediately before its one `videos.update`, read-back and audit (`source: upload_localizations`); the upload also sends the package's `status.containsSyntheticMedia` (absent: the channel's setting). The video gets its `publishAt` only after the translations, thumbnail, playlist and read-back passed (BL-224). A weekly-plan slot's date reaches a video only (a) when the slot matches the channel's **week template that the owner approved or edited himself in the Web UI** (`week-template/1`, 2026-11-16, owner msgs 4569/4575/4620/4630–4636, BL-267, ADR 0073) and, on a channel whose owner reviews its packages, the owner approved that video's media in Media → «Видео на проверку»; or (b) through the owner's explicit one-slot «Дать дату вне шаблона» in the Web UI; or (c) by an explicit **move** of a slot whose video already has a date, by the owner (Web UI) or the Producer (`producer_publishing_plan_move_slot`, its own endpoint only), to any day, time or week -- written at once through `src/lib/video-details/` (identity check, backup, Live writes immediately before, read-back, audit), never for a public video, never within 15 minutes, and never as a first date. Always only on the computer whose automatic-upload switch is on (a move: the computer that uploaded the video). A template match gives only a first date of an undated private video, never moves one; the plan-schedule pass otherwise changes or removes only a date that computer itself set (the owner's explicit date, a veto); a date set elsewhere (YouTube Studio, «Видео», the other computer) is changed only by an explicit move, and a template change never moves or removes a date. A veto removes a date the app set (still private) through `src/lib/video-details/`. A slot dated by (a) or (b) also authorizes its release package's social posts (`crossPost`, ADR 0068), as does a slot whose video carries that computer's own date at the slot's time (owner msg 4640: the social networks duplicate YouTube); never a foreign date. Each network posts or stops on its own identity check (owner TG 4779, ADR 0068 amendment 2). A social post more than 12 h late is sent only on the owner's explicit «Повторить» in the Web UI of a failed job that never sent its publishing call (owner TG 4780), still under the same slot authorization; agents have no such retry. Agents never approve or withdraw a template, give a first date or veto: the Producer may propose a template and move slots as above; the Operator and channel workers cannot move a slot or re-time a slot whose video has a date. (`docs/PROJECT_SPEC.md` §21).

  **Producer upload queue (2026-11-01, owner, Telegram msgs 3928/3930, BL-239, ADR 0059):** the Producer (only it, only on its own endpoint) may order this computer's upload queue, cancel a queued upload (since BL-244, ADR 0064, owner msgs 4046/4050: also stop one being sent before its last chunk) and add a ready package through `src/lib/publishing/` on the computer whose automatic-upload switch is on -- the same checks and runner as the automatic upload, private, a date only by the weekly-plan rule above. Channel worker agents and the factory get no upload tool.

  **Thumbnail writer (2026-11-15, owner, Telegram msgs 4380/4383, BL-255, ADR 0069):** `src/lib/video-thumbnails/` may write the custom thumbnail (`thumbnails.set`) of a video already on YouTube, any video of the channel -- for the owner (Web UI) and the Producer (`producer_video_thumbnail_replace`, its own endpoint only), only an image under `04 Videos/` of the channel's workspace (JPEG/PNG, at most 2 MB), refused while this computer's upload of the video has not yet run its own thumbnail step, with identity check, backup of the current thumbnail, Live writes immediately before the call, read-back and audit; nothing else of the video, the plan or the package changes. Channel worker agents and the factory get no thumbnail tool (`docs/PROJECT_SPEC.md` §21).

  **Owner package review (2026-11-15, owner, TG 2298 via the Producer, msgs 4514/4516, BL-257, ADR 0070; amended 2026-11-16, BL-265, ADR 0072):** not a YouTube writer -- a gate. For a channel whose owner turned it on (WWE), a release package counts as ready (weekly plan, automatic upload, Producer queue add, owner upload approval) only after the owner approved its **media** in Media → «Видео на проверку» -- the mp4 (`sha256` + `sizeBytes`, per channel and video code, or its BL-263 recode alias); packaging changes (texts, thumbnail, translations) neither need nor reset it, and packaging gets the owner's comments, which block nothing. A decision made before BL-265 still covers its own manifest. The upload runner re-checks it before the first byte. Only the owner's Web UI decides or switches it (`src/lib/package-reviews/`).

  **Package metadata after upload (2026-11-16, owner, Telegram msgs 4566–4569, BL-265, ADR 0072):** `src/lib/publishing/` may write a video's default-language `snippet.title`, `snippet.description` and `snippet.tags` -- only of a video that a release package of the channel already put on YouTube (its upload record names the video id), only the values that package's current manifest states (never free text), only through `src/lib/video-details/` as a full read-merge-write of `snippet` (`categoryId`, `defaultLanguage` and `defaultAudioLanguage` sent back exactly as read just before the write; `zxx` left out as today), with a three-way conflict check (YouTube now / what the upload sent / the manifest), identity check, backup of the current snippet, Live writes immediately before the call, read-back (the written fields, and the untouched snippet fields, privacy, `publishAt` and the localization languages unchanged), audit (`source: package_metadata`, actor owner/producer) and a dry run. Only for the owner («Применить упаковку» in the Web UI) and the Producer (`producer_video_metadata_update`, its own endpoint only, refusing any conflict); refused while this computer's upload of that video has not finished its read-back. Never `status`, `publishAt`, category or languages; never automatically from a new manifest. Channel worker agents and the factory get no such tool.

  *Amended 2026-11-24 (owner TG 4839/4842, «согласовываю», after the Producer's relay TG 2578; ADR 0072 amendment):* the same two callers may also write the video's per-language `localizations` title/description -- only the languages and values of that package's **current manifest** `localizations` (the set the upload's translations step sends, `packageLocalizationSet`; never free text), never the video's own default language (YouTube's `snippet.defaultLanguage`; that text stays BL-265's snippet path), only through the shared video translations writer `src/lib/shared-video-localizations/` (source `package_localizations`; no new writer, no new gateway function), with a per-language, per-field three-way check (YouTube now / what this computer's upload sent -- its finished upload row when the translations step read back `verified`, or none sent when it was `none`, or the latest verified fix here; otherwise unknown -- / the package): equal, written, or a conflict, and **any conflict refuses the whole call for the owner and the Producer alike** (no override). A language the video has and the package lacks is kept, nothing is ever removed, and the snippet is sent back exactly as read; one YouTube write per call (`producer_video_metadata_update { localizations: true }`, the owner's «Переводы упаковки» → «Применить переводы»). Identity check, backup of the current translations, a recheck that each language written still reads as checked right before the write (else nothing is sent), Live writes immediately before the call, read-back (written languages, kept languages, the snippet, and privacy and `publishAt` unchanged), audit (`source: package_localizations`, actor owner/producer), dry run, and the same refusal while this computer's upload of the video has not finished its read-back.

  **Captions writer (2026-11-16, owner, Telegram msgs 4590/4592, amended 2026-11-17 msg 4660, FO-REQ-0055, BL-269, ADR 0074):** `src/lib/video-captions/` may insert one English caption track (`captions.insert`) and, only on an explicit overwrite by the owner («Перезаписать субтитры» in the Web UI, after a dry-run preview and an in-app confirm) or the Producer (`producer_video_captions_add` with `overwrite: true`), replace the content of the video's one English standard track, foreign or the app's own (`captions.update` of that track id); never `captions.delete`, never an ASR track. Only on a channel whose captions switch the owner turned on (WWE) and only on a horizontal long video, only the file a release package of that channel states (`captions`, checked by `packageProblems`: SRT/WebVTT, SHA-256, size, `en`). Two paths: the upload step of `src/lib/publishing/` (after the translations, before the thumbnail; it never overwrites -- an existing English track refuses the step; the video gets its `publishAt` only after the captions step and the read-back passed) and, for a video already uploaded by a package, the owner's Web UI and the Producer (its own endpoint only), from that package's current manifest. Identity check, backup (the track list; for an overwrite also the replaced track's content, `captions.download` -- no backup, no write), Live writes immediately before the call, read-back (`captions.list`), audit, dry run and the quota guard. Channel worker agents and the factory get no caption tool (`docs/PROJECT_SPEC.md` §21).

  **Playlist editing by agents (2026-11-23, owner, Telegram msg 4782, amending ADR 0048 rule 2):** «нужно дать права продюсеру и агентам каналов редактировать плей листы. Добавлять / удалять оттуда видео. И делать их видимыми / приватными.» The playlist core `src/lib/playlist-management/` (one writer for the owner's Web UI, the operator and the agents; every write through `src/lib/youtube-write-gateway/` with `assertLiveWritesAuthorized` immediately before it) may, for a **channel worker** (its own bound channel only) and for the **Producer** (any channel connected on this computer, on its own endpoint, one channel per call in that channel's agent scope): create a playlist, change its title, description and privacy (`private`, `unlisted` or **`public`**), add videos to it and remove videos from it -- tools `playlist_list` (read), `playlist_create`, `playlist_update`, `playlist_add_videos`, `playlist_remove_videos`; a worker also `agent_set_privacy` with `target: playlist` (public included). Checks on every write: the write-channel guardrail (`write-context.assertWriteChannel`; in an agent scope `expectedChannelId` must be the scope's channel, refused before any credential or YouTube call), the playlist's owner channel (read before the write), and for the Producer's `playlist_add_videos` only the channel's own videos in its local synced list (`not_found` otherwise, before any call). Every worker call is in the worker log (ADR 0048 §5), every Producer call in the Producer call log, refused calls included. **Not authorized:** a playlist delete (`playlist_delete` stays owner/operator-only), and making a **video** public -- `agent_set_privacy` with `target: video` stays private/unlisted (`AGENT_PUBLIC_NOT_ALLOWED`); the Producer gets no `agent_set_privacy` at all. The factory gets no playlist tool.
